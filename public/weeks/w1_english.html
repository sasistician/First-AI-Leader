Recap · From Week 0 02 — 22
before today

You already know what a harness is — in general.

Five components, one loop: perceive → plan → act → observe, governed by tools, context, permissions, and memory. That's the shared vocabulary from Week 0.

  • Tools — what the harness can execute.
  • Context — what the model can currently see.
  • Permissions — what it may do unsupervised.
  • Memory — what persists between sessions.

Today, all of this becomes concrete — because Claude Code is a specific instance of this pattern, not a new one.

The Bridge · Part 1 03 — 22

Claude Code is one particular, opinionated implementation of that same loop.

Same five components. Same loop. But now with a specific set of tools, a specific set of permission modes, and a specific surface — your terminal, on your actual repo. First: chatting vs. directing.

The Core Distinction · Part 2 04 — 22
the distinction that changes everything

Chatting and directing look similar. They are not the same thing.

The shallow end Chatting One-shot Q&A. You ask, it answers, and you take the output and do the work yourself. The loop happens in your head, not the tool's.
The frontier Directing A bounded, multi-step task handed off. The agent runs its own perceive → plan → act → observe loop, checking in only where you've told it to.

Every week from here assumes directing. Today's lab puts you in the seat.

Made Real · Part 2 05 — 22
a real project, not a hypothetical

Building a RAG agentic system for customer service reps was never a "chat."

The goal: a retrieval-augmented agent that helps customer service reps answer policy and offer questions accurately. The work was days of multi-step integration — wiring into Amazon Bedrock for the underlying models, connecting to our internal deployment environment, and integrating a promotions API and other internal tools. None of that happens in one prompt-response pair.

  • Read and adapted existing integration code, across multiple services.
  • Wrote and ran tests against the Bedrock-backed retrieval pipeline.
  • Iterated across files, not in one window — each step fed the next.
  • That's the agentic loop, running on a real system, for real stakes.

The Loop In Practice · Stage 1 of 4 07 — 22
01 Perceive

Claude Code reads your prompt, the current state of the repo, and every tool result so far — that's "perceive," every single step of the loop.

from the rag project

Perceiving meant reading existing Bedrock integration code, the internal deployment environment's config, and the promotions API's documentation — before writing a line.

The Loop In Practice · Stage 2 of 4 08 — 22
02 Plan

It decides the next tool call — read this file? run this test? edit this function? — based entirely on what it just perceived.

from the rag project

Planning meant deciding: look at the embedding pipeline next, or the API client first? Claude Code does the same triage, every single step.

The Loop In Practice · Stage 3 of 4 09 — 22
03 Act

It executes the plan for real — on disk — via Bash, Edit, Write, and every other tool. Not a suggestion in a chat bubble. A real change.

worth sitting with

This is the step where "directing" stops being a metaphor. Whatever it decided in the plan step, it now actually does — which is exactly why the next stage, and this week's permission modes, matter so much.

The Loop In Practice · Stage 4 of 4 10 — 22
04 Observe

The result of the action — a test pass, a test fail, a file's new contents — becomes new context. The loop repeats with that new information already perceived.

↻ perceive → plan → act → observe → repeats until the task is done
Permission Modes · The New Layer 11 — 22
what governs "act"

Four modes, four very different amounts of friction.

DefaultAsk before each write
What happens

Every file edit or risky command pauses for your approval, one at a time.

Good for / tradeoff

Unfamiliar code, high-stakes changes. Safer, slower.

Plan modePropose, then approve
What happens

Claude lays out its full approach before taking any action at all.

Good for / tradeoff

Multi-step or ambiguous tasks. One review instead of many — but you must actually read the plan.

Auto-accept editsApply, review after
What happens

Edits apply immediately; you review the diff afterward instead of approving each one.

Good for / tradeoff

Fast iteration on trusted ground. Fast — until you stop actually reviewing.

Bypass permissionsNothing pauses
What happens

The full loop runs unattended, start to finish. Invoked separately from the other three — a startup flag, not something you cycle into mid-session.

Good for / tradeoff

Sandboxes, low-stakes batch work. Highest leverage, highest blast radius.

The first three are something you cycle through during a session. Bypass is a separate, riskier switch you choose deliberately, up front.

Permission Modes · The Real Cost 12 — 22
a real cost, not a hypothetical

Auto-accepting without paying attention once cost us a working RAG system.

On that same customer-service RAG project, the habit was to auto-accept edits and document ingestion without closely reviewing each one. At one point, that habit let outdated, since-superseded policy documents get ingested into the knowledge base. Nobody caught it until accuracy had already degraded — the fix meant rolling back to a previous working version and redoing real work.

To be precise: that auto-approval was in the ingestion pipeline, not Claude Code's own permission modes — a different system, a different failure surface. A bad code edit shows up in git diff; a bad document in a knowledge base usually doesn't, until the answers get worse. But the habit that caused it — approving without actually looking — is exactly the habit Claude Code's permission modes let you build or break.

The setting wasn't the problem. Using it without attention was.

permission modes aren't a settings choice — they're a habit you build
Terminal-As-Leverage 13 — 22
why the terminal, not a chat window

The terminal is the highest-leverage surface for directing an agent.

  • Multi-file edits, applied in one pass, not copy-pasted one at a time.
  • Real test suites, actually run — not described, executed.
  • Git, actually committed — history you can inspect and revert.
  • Composed with every other CLI tool you already use.
the polyglot problem this solves

Different products often require different languages and environments — C here, Java there, Python somewhere else. Claude Code works the same way regardless: one harness, not per-language tooling.

Discovery Work 14 — 22
not every task starts with a clear spec

Sometimes integrating with an existing environment means discovery before action.

When the instructions for plugging into an existing system aren't fully spelled out, part of directing the agent is letting it explore first — read the code, check how things are wired — before it gets to the part that produces output.

That's not a sign you picked the wrong task. It's normal. Watch for it in today's lab, and again in your own reps this week.

Lab Walkthrough · Step 1 of 4 16 — 22
hand off the task

One direction, not a back-and-forth chat.

Lab Walkthrough · Step 2 of 4 17 — 22
watch, don't just wait

Watch it perceive and plan — not once, but on repeat.

It reads the file and sketches an approach before the first edit — but on a real refactor, it doesn't stop there. It keeps re-reading and re-planning between edits: check a function, write it, re-check the next one, adjust. Perceive and plan recur continuously through the whole task, not just once at the start.

If you only look at the final diff, you miss the part that's actually new this week.

Lab Walkthrough · Step 3 of 4 18 — 22
on purpose, this time

Try a different permission mode mid-task — deliberately.

Redo a slice of the task under a mode you didn't start with. Notice exactly what changes in how the loop feels — not just whether it worked.

This is the moment slide 12's habit becomes a choice you're making on purpose, not a default you've stopped noticing.

Lab Walkthrough · Step 4 of 4 19 — 22
close the loop

Run the tests. Confirm green. Notice if it self-corrected.

Run the new tests and the script itself. If a test failed at first, watch what happens next — did it read the failure and fix it before telling you it was done?

That self-correction is the observe step, doing exactly what it's supposed to do.
