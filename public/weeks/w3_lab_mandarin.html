本周实验深度解析 · evbot

EVBot。

一个真实系统，六个组件，每个决策都清晰可见

这周的课程讲了 Skill——把一个反复出现的流程打包起来，这样 Claude 不用你每次重新 解释就能调用它。EVBot 正是这堂课的载体：这是一个真实、可运行的电动车问答聊天机器人—— 每个问题在到达你面前之前，都会经过检查、路由、检索、生成答案、评判和安全检查。

这份讲义包含什么
  • 完整流水线——运行了什么、按什么顺序运行、什么情况会提前结束请求
  • 护栏、路由器、RAG、评判模型和记忆——每一个到底决定了什么
  • Gradio 调试面板和 uv——你将如何查看和运行这一切
  • 评判模型的评分标准，打包成一个 Claude Code Skill
  • 六步实验练习本身，对照你刚学到的内容

不只是这六个部分存在——而是为什么每一个都是这样构建的。

流水线 · 一次查询，从头到尾 02 — 10
整条流水线，一次查询的完整过程

在你看到答案之前，会运行九个步骤——其中两个可能提前结束请求。

  • 1. 读取会话记忆 —— 本次会话最近的对话轮次，让代词类的追问能被正确解析。
  • 2. 输入护栏 —— 主题相关性检查；离题问题会在这里退出，在其他任何环节运行之前。
  • 3. 路由器 —— 判断查询是简单还是复杂；这是一个基于规则的决策，不调用 LLM。
  • 4. RAG 检索 —— 从 Chroma 知识库中取出相关的电动车文档。
  • 5a. 简单路径 —— 由小模型直接生成一个答案，直接进入输出护栏。
  • 5b. 复杂路径 —— 生成两个候选答案，小模型和大模型各一个，使用相同的检索上下文。
  • 6. 评判模型（仅复杂路径） —— 为两个候选答案打分，并选出或合并出一个胜出答案。
  • 7. 输出护栏 —— 扫描最终答案中的个人身份信息、不当内容和缺乏依据的说法。
  • 8. 写入会话记忆 —— 这一轮对话被持久化保存，完整的追踪记录会显示在调试面板中。

这九个步骤里有两个是提前退出——会跳过后续所有环节——这是刻意设计的，也是接下来两页的主线。

护栏 · 每个答案的前后把关 03 — 10
每个答案前后都会运行什么

两道护栏，两种不同的职责——一道防止坏输入触达模型，另一道防止坏输出触达你。

输入护栏是一次快速的、以确定性规则为主的关键词匹配，针对电动车相关词汇；只有在情况 模糊时，才会退回到一次性的 LLM 分类调用——而且这次调用会拿到对话历史，这样像"它多少钱？" 这样的追问就能正确解析代词，而不会被误判为离题。输出护栏则打包了三项检查：个人身份信息 （PII）的正则扫描、基于关键词的不当内容检查，以及一个 LLM 依据性检查——它会把答案的每 一句话标记为"有依据支持"或"无依据支持"，对照检索到的上下文。

  • 输入护栏会在路由器、RAG 或任何模型调用运行之前就拒绝/引导离题问题——在调试面板中显示为 early_exit: true。
  • 输出护栏的依据性检查，正是"这在我的知识库里没有"这种诚实回退回答的来源，而不是一个听起来很自信的猜测。
  • 两道护栏都是"确定性规则优先，LLM 兜底在后"——先跑便宜的检查，再跑昂贵的检查。

一个说不清自己为什么拦截了内容的护栏，只是一个过滤器。这一个每次都会在调试面板里展示它的推理过程。

路由器 · 关乎成本，而不只是能力 04 — 10
决定一个查询该用哪个模型——以及走多少流程

路由器真正做的决定，不是哪个模型来回答。而是评判模型到底要不要运行。

classify_complexity() 是基于规则的，不是一次 LLM 调用——依据字数、比较类 关键词（"compare"、"vs"、"pros and cons"），以及多模型提及检测。一个简单的事实性问题会 由小而快的模型直接给出一个答案，然后直接进入输出护栏。一个复杂或比较类的问题，会生成两个 完整的候选答案——小模型和大模型各一个，使用同样检索到的上下文——只有到这时，评判模型才会 被调用来在两者之间做出选择。

  • 简单路径：1 次模型调用，0 次评判模型调用。
  • 复杂路径：2 次模型调用，1 次评判模型调用（而评判本身又是一次模型调用）。
  • 这是一个成本/延迟的杠杆，不只是质量的杠杆——大多数问题并不需要第二意见。

每一次"复杂"查询的模型调用成本大约是"简单"查询的 3 倍。路由器的职责，就是确保这个成本只在问题真正需要的时候才被付出。

RAG · 答案到底从哪里来 05 — 10
答案究竟从哪里来

知识库里是真实的电动车品牌、真实的参数，也刻意留有缺口——这些缺口就是作业，不是缺陷。

data/ev_docs/ 里是真实品牌的内容——特斯拉 Model 3、Rivian R1T、福特 Mustang Mach-E、雪佛兰 Bolt、现代 Ioniq 5——覆盖车型参数、充电、补贴政策和电池/维护四个 类别，每一份都明确标注了日期，并说明是示意性内容而非实时报价。摄取脚本 （evbot/rag/ingest.py）手工对 Markdown 分块，通过 Chroma 内置的本地 ONNX 模型做嵌入（不需要外部嵌入 API 密钥），并且每次运行都会幂等地重建整个集合。

  • 这一阶段没有网页搜索——刻意只用 RAG，这样检索这一步就容易推理。
  • 知识库里完全没有电动车保险费用的信息——这个缺口正是实验练习第4步要暴露出来的东西。
  • 检索深度（k）在复杂/比较类查询里比简单查询更大——一个比较类问题需要更多的文档块，才能把两辆车都讲清楚依据。

一个不完整的知识库不是需要隐藏的缺陷——配合输出护栏的依据性检查，它正是让"我不知道"成为一种可见的、正确的行为，而不是一次静默的失败。

LLM-as-judge · 打分，而非生成 06 — 10
评估质量，而不是生成内容

评判模型从不自己写答案。它唯一的工作，是决定两个候选答案里哪一个配得上呈现给你。

对于复杂查询，judge.py 会把两个候选答案——都基于完全相同的检索上下文—— 连同一份四项标准的评分标准（准确性、完整性、依据性、清晰度，每项 1-5 分）一起发给更大的 本地模型。评判模型随后应用一套决策策略：选出明确的胜出者，或者合并两者中最强的部分，并 给出解释这次判断的理由。

  • 两个候选答案使用相同的检索上下文——评判模型比较的是模型质量，而不是谁拿到了更好的信息。
  • 输出是一个 JudgeResult：胜出者、合并后的答案、理由，以及完整的分数明细——全部都能在调试面板里看到。
  • 评判本身运行在更大、更强的模型上——评判被视为比回答更难的工作。

这正是本篇讲义后面会被打包成 Claude Code Skill 的那一部分——一套值得单独调用的评分标准，而不只是埋在一个文件里。

记忆 · 两套系统，两种职责 07 — 10
两个都叫"记忆"的系统，做着两件不同的事

会话记忆记住的是你的对话。知识库记住的是这个世界。把两者混为一谈，会同时破坏两者。

evbot/memory.py 是一个基于 SQLite 的对话日志——append_turn 和 get_recent_turns——它会跨应用重启持久保存，并且在每一轮对话开始时都会被 读取，这样代词类的追问才能被正确解析。它在架构上和 RAG 检索时使用的 Chroma 知识库是 完全独立的：一个随着每次对话不断变化，另一个只有在有人重新摄取文档时才会变化。

  • 会话记忆：按会话独立、不断增长、跨重启保留，和电动车事实本身毫无关系。
  • 知识库：所有会话共享、只有在重新摄取时才变化，和是谁在提问毫无关系。
  • 实验练习第5步直接测试了这一点：在对话进行到一半时重启应用，确认记忆能保留下来，而知识库完全没有变化。

如果这两者存放在同一张表里，添加一份电动车文档看起来就会像是"这个机器人从和你的对话里学到了什么"——但事实并非如此，而且会让调试变得困难得多。

你能看到的界面，和背后运行的一切 08 — 10
你能看到什么，以及背后运行的是什么

特意加了第二个面板，就是为了让这个系统里没有任何一处是黑箱。

app.py 构建了一个 Gradio gr.Blocks 界面——刻意没有用更高层的 ChatInterface——因为它需要在聊天面板旁边再放一个"幕后"面板，展示每一轮对话 的完整追踪记录：护栏的判定结果、路由器的决策、检索到的文档片段、候选答案、评判模型的分数 和理由（如果评判运行了的话），以及记忆的读写情况。而在这一切之下，uv 管理着 Python 环境——pyproject.toml 加上一份提交到仓库的 uv.lock——这是 本课程第一次用到 uv。

  • 这个调试面板不是摆设——实验练习里的每一个检查点，都是"确认调试面板显示了 X"。
  • 选 gr.Blocks 而不是 ChatInterface 是刻意的取舍：多写一些代码，换来对第二个面板的完全控制。
  • uv run pytest、uv run python -m evbot.rag.ingest、uv run python -m evbot.app——同一个环境，三个不同的入口。

可观察性是这个实验的硬性要求，而不是事后补上的东西——你不应该需要靠猜测，才能知道是哪个组件做出了某个决定。

回到这周真正的课程内容 09 — 10
回到这周真正的课程内容

评判模型的评分标准，是 EVBot 里唯一真正值得打包成 Skill 的部分——这里说明为什么护栏不是。

.claude/skills/answer-quality-judge/SKILL.md 把评判模型的四项评分标准和 决策策略打包成了一个可调用的 Skill——它的 frontmatter 描述会在"给这两份答案打分"或 "哪个回答更好"这类提示词上触发，而且它的字段名和 judge.py 里的 RUBRIC_PROMPT 完全一致。输入/输出护栏则刻意没有这样打包：它们是廉价的、 确定性的、为了延迟而内联的检查，不是一个值得在应用之外单独调用的多维度判断。

  • 这周课程里的同一套检验标准：它是否在不同场景里反复出现、是否是一个判断（而非机械执行）、能否用一句话说清楚、做错了是否会造成真实代价——评判模型的评分标准四项全过，护栏的关键词扫描完全不需要。
  • 实验练习第6步会让你把 SKILL.md 和 judge.py 的评分标准做对比，然后在一次 Claude Code 会话里直接对两份粘贴进去的答案调用这个 Skill。

整个应用已经在运行这套评分标准了。这个 Skill 存在的意义，是让你不用打开 judge.py，就能在任何两个答案上跑同一套判断，随时随地。

实验练习 · 六个步骤，六个检查点 10 — 10
你实际会做的事，一步一步来

六个步骤，六个检查点——每一个都是为了让某个具体的架构决策，在调试面板里清晰可见。

  • 1. 一个简单的、知识库内的问题——确认评判模型是 null；路由器跳过了它。
  • 2. 一个离题问题——确认 early_exit: true；路由器/RAG/评判模型都没有运行。
  • 3. 一个真正的比较类问题——确认两个候选答案都出现了，并读一读评判模型给出的理由。
  • 4. 一个知识库没覆盖的问题（电动车保险费用）——确认得到的是诚实的"这不在我的知识库里"回退回答，而不是一个猜测。
  • 5. 一次带代词追问的两轮对话，然后重启应用——确认记忆在重启后依然保留，而知识库完全没有变化。
  • 6. 打开 SKILL.md，对照 judge.py——确认评分标准一致，然后直接对两份粘贴进去的答案调用这个 Skill。

以上每一个检查点都对应本讲义里的一页——如果某个检查点的行为和对应那一页预测的不一样，那正是调试练习本身，而不是对它的干扰。
