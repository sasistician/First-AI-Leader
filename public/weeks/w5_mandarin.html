回顾与承接 · 来自第3-4周 02 — 30
你带着走进来的东西

两块能跑的拼图，还不是一个系统。

这两块拼图本身都没毛病。EVBot 的 Skill 能跑，MCP 服务器能连——你已经在各自的实验课里 亲手验证过了。缺的是架在它们之上的那一层东西。

  • EVBot（第3周）：护栏、路由器、RAG、打包成 Skill 的 LLM-as-judge 评分标准、会话记忆、一个 Gradio 界面——全部本地运行，全部对内。
  • MCP 服务器（第4周）：一个实时网页搜索工具，已注册到 Claude Code，并针对 EVBot 文档答不出的那个保险费用问题做过实测。
  • 两者都做不到的事：决定什么时候该用哪一个、检查任何一方的输出、在坏答案抵达用户之前拦下它。
回顾与承接 · 来自第3-4周 03 — 30
还缺的那一环

没有人在盯着输出。

眼下，就算 EVBot 自己的评判模型按自己的评分标准给某个答案打了1分（满分5分），或者 MCP 工具返回了一堆垃圾，也没有任何东西能拦住它们抵达用户。没有一个主智能体来决定该不该信任 这两块能干的拼图，也没有一套可重复的方法能在上线之前证明合体后的系统真的够格。

  • 编排：谁来决定哪个智能体负责什么，谁来检查结果。
  • 护栏：什么能在坏输出上线或行动之前拦住它。
  • 评估：怎么用证据而不是感觉，证明"足够好"。
回顾与承接 · 来自第3-4周 04 — 30
重新框定

从"演示里跑通了"到"真的能上线了"。

上一页的每一道缺口，形状都一样：一个智能体不管多能干，都不可能同时又是独立检查自己 工作成果的那个角色。生成和验证是两份不同的工作——把它们混在一起，就意味着同一个盲点会 在两处都出问题。

这正是今天三块内容要合力解决的——谁委派给谁、什么能拦住坏输出、以及你怎么证明它够好。从编排开始。

编排模式 · 第1部分 05 — 30
单智能体的天花板

一个智能体，一条推理线索，太多份工作。

让一次智能体调用既生成答案、又给自己的准确性打分、还要判断能不能安全上线——这等于 让它自己批改自己的作业：同一个盲点会在每一步都冒出来，而不会被真正拦下来。

  • 生成和验证是两份不同的工作——把它们塞进同一个智能体，意味着同一个盲点会同时覆盖两边。
  • 相互独立的智能体可以同时运行——这带来的是实际耗时更短，而不只是质量更好。
  • 主智能体不需要比它的工作者更聪明——只需要知道什么时候该扇出任务、以及怎么把结果合并回来。
编排模式 · 第1部分 06 — 30
两个角色，直接借自 claude code 本身

主智能体与子智能体——每一种模式背后的两个角色。

在看下一页的三种形态之前，先看它们共用的这两个角色。主智能体负责规划、委派， 并决定怎么合并回收到的结果——它不需要亲自去做那些细分的具体工作，只需要知道什么时候 该交出去。子智能体由主智能体针对某一项任务专门启动，拥有自己独立的上下文 窗口——它不会继承主智能体的完整对话，只管完成自己的任务、返回一个结果，然后它的 上下文就会消失。

  • 这不是一个假设性的抽象概念——它正是 Claude Code 自己用来为某项限定任务运行子智能体的真实机制，也正是今天实验课里你会直接指挥的那一个。
  • "监督者"（下一页的模式名称）和"主智能体"（角色名称）说的是同一件事——本课程里两者可互换使用。
  • 子智能体拥有独立的上下文窗口，这是一个特性，而不是局限：这正是为什么一个负责评分的子智能体不会继承生成者子智能体犯下的错误。

下一页的每一种模式，都是这两个角色以不同方式组合出来的。

编排模式 · 第1部分 07 — 30
三种形态，一个理念：有意识地委派

监督者、流水线、并行扇出。

监督者 / 工作者
一个规划者，多个执行者
主智能体负责规划与委派；工作者执行各自限定的任务；结果返回给主智能体统一合并。
流水线
每一环都喂给下一环
生成者的输出成为检查者的输入，再成为合成者的输入——按顺序依次运行，而非同时进行。
并行扇出
各自独立的工作，一道屏障
互不依赖的工作者并发运行；一个同步点会等所有人都完成后再统一合并。

大多数真实系统会把这几种混在一起用——今天的实战示例正是如此。

编排模式 · 第1部分 08 — 30
不是每项任务都需要一整支小队

当工作确实相互独立时，才委派出去。

什么时候该留在单智能体

任务本身很小、上下文已经加载好了、每一步都依赖上一步的结果，或者协调的开销会超过它带来的收益。

什么时候该委派给一整支小队

各项任务不依赖彼此的输出、每一项都需要一个独特的视角，而且你有意希望它们并发——或独立地——运行。

最后这一点比听起来更重要：一个与生成者共享上下文的评分者，很可能会继承它的盲点，而不是发现它。

编排模式 · 第1部分 10 — 30
正是第1部分讲过的那个模式

三个工作者并行，然后一道屏障，然后一个裁决。

扇出 评分员 + 检查员 + 测试员同时运行 相互独立、不共享上下文——与此同时，生成器在旁边为明天的批次继续工作。
→
屏障 合成员在等待 在三个工作者的输出都到齐之前，不会有任何进展——这是唯一一个刻意设置的同步点。
→
合成 一张记分卡，通过或不通过 对照发布阈值检验。这就是护栏关卡的开合所在。

扇出、屏障、合成——独立的工作并行进行，闯关之前设一个刻意的检查点。今天的实验课里，你会亲手跑一遍一模一样的流程。

护栏 · 第2部分 11 — 30
为什么"模型通常是对的"还不够

没有任何东西检查输出时，会出什么问题。

  • 一个凭空捏造的具体细节——一个价格、一条政策规定——读起来和正确答案一样自信满满。用户分辨不出差别；护栏必须能分辨。
  • 一个拥有宽泛工具权限的智能体，可能因为一条错误指令就采取一个无法撤销的行动——这正是第4周 MCP 检查清单里"权限过宽"那条风险，只是现在出现在编排这一层。
  • 没有关卡的话，"演示里看着没问题"就是你上线前唯一的证据。
护栏 · 第2部分 12 — 30
最小权限原则，贯穿整个编排

限定每个智能体——以及每个工作者——能碰到什么。

  • 只给每个工作者它的任务需要的工具和数据——评分员不需要写权限；生成器不需要发布任何东西的权限。
  • 把任何执行代码或调用外部工具的东西都放进沙箱，和第4周 MCP 服务器一样的信任边界原则，现在应用到小队里的每一个智能体。
  • 记录每个智能体实际做了什么——你没记录下来的决策，就没法审计。

第1周讲过的 Claude Code 自己的权限模式，就是实现这一点的一种具体机制——同样的原则，从单个智能体一路扩展到一整支小队都适用。

护栏 · 第2部分 13 — 30
有些决定还是得由人来做

审批关卡：自动化刻意止步的地方。

不是所有事情都该完全自主运行。某些行动——不可撤销的、后果重大的、置信度低的——应该 先暂停，等一个人批准之后再继续。

  • 不可撤销的行动——发送、删除、花钱——不管置信度分数多高，都要设关卡。
  • 低置信度或处于临界值的输出，应该转给人来处理，而不是靠猜蒙混过关。
  • 关卡本身需要一个明确的负责人——一个要为放行内容担责的人。
护栏 · 第2部分 14 — 30
来自一个真实项目

一个不过关就不上线的银行聊天机器人。

来自一家大型银行的客户端聊天机器人项目

我们没法靠"看着没问题"就上线。每一次发布都必须闯过一道关卡：在触达任何一位客户之前， 先对着一个真实数据集通过严格测试——一致性和减少幻觉，是这项工作本身的核心目的， 而不是事后才想起来补的一环。

  • 几百组真实的问答对，专门用来测试一致性和幻觉问题。
  • 不闯过关卡就不能上线——这道护栏是流程性的，不只是技术性的。
评估 · 第3部分 15 — 30
第2周的同一套纪律，这次对准评估

那些场景是扎根的，不是凭空编出来的。

那几百组问答对不是泛泛的常识题——它们全都建立在真实的产品与政策文档之上， 和第2周应用在 CLAUDE.md 与 RAG 上的那套扎根纪律一模一样，只是这次用来构建 测试集本身。

  • 泛泛的测试问题只能抓住泛泛的错误。真实的、扎根于上下文的场景，才能抓住生产环境里真正会发生的失败。
  • 这正是小队里场景生成器这个工作者在做的事——基于 EVBot 的真实文档生成，而不是凭空编造。今天小队用的种子集比"几百组"要小得多；但不论规模大小，这套纪律都是一样的。

构建评估数据集本身就是一种上下文工程。它值得和给智能体本身打地基一样的用心。

评估 · 第3部分 16 — 30
不是全自动，也不是全靠人工

先用 LLM-as-judge 过一遍，被标记的再交给人复核。

对照问答数据集做自动评分，能又快又省地抓住大部分问题。处于临界值或被标记的案例， 在任何东西上线之前，都会交给人工复核。

  • LLM-as-judge 能规模化——每次发布，几百组问答对都能被快速、一致地评完分。
  • 人工复核能抓住评判模型自己也不确定的、或者压根没被设定去抓的问题。
  • 和第3周 EVBot 自己那个评判 Skill 是同一个模式——只是加了一条：置信度低于某个阈值时，转给人来处理。
评估 · 第3部分 17 — 30
不只是这个故事，更是这套模式

拿证据说话，别靠肉眼判断。

  • 构建一个真实的评估数据集——用扎根的场景，不用泛泛的场景。
  • 大规模自动评分，低置信度的案例升级给人工处理。
  • 设一个数字阈值，并把它当作硬性关卡来执行——而不是一个建议。
  • 每一次有意义的改动之后都重新跑一遍评估，而不是只在首次上线前跑一次。
评估 · 第3部分 18 — 30
没有单一的灵丹妙药

扎根、护栏、评估——三者合力，缺一不可。

扎根（第2周）
答案绑定真实来源
RAG 与上下文工程，在模型给出任何答案之前，先给它一个站得住脚的真实依据。
护栏
在上线之前拦下它
权限、沙箱和审批关卡，阻止明显错误或不安全的输出抵达任何人。
评估
证明它在规模化下依然有效
一个真实数据集加一套混合评判机制，把"感觉还行"变成一个你能拿出去辩护的数字。

少了任何一层，另外两层都会在为一个自己看不全的缺口兜底。

评估 · 第3部分 19 — 30
在你宣布完工之前

这份检查清单。

  • 每一个不可撤销或后果重大的行动，都有一道审批关卡，或者干脆被排除在自主执行的范围之外。
  • 每个智能体的工具权限都和它的工作相匹配，不多不少。
  • 存在一个真实的评估数据集，扎根于真实场景，并设有一个数字化的通过阈值。
  • 评分采用混合模式：大规模自动评分，临界案例人工复核。
  • 每一次有意义的改动之后都会重新跑评估——而不是一次性的关卡。
  • 有明确的人对关卡放行的内容负责。

毕业项目 · 第4部分 21 — 30
同一套模式，你自己的角色

一个主智能体，以及由你的问题塑造出来的工作者们。

今天的小队——生成器、评分员、依据性检查员、测试员、合成员——只是这套模式的一个具体 实例。你的毕业项目需要自己的一套阵容，由你系统里真正可能出问题的地方来塑造。

  • 你的系统里，哪些任务真正相互独立——值得为它专门配一个工作者？
  • 你的护栏关卡是什么，它执行的是什么阈值？
  • 你自己的评估数据集实际上应该包含什么？
毕业项目 · 第4部分 22 — 30
怎么评分

及格 = 全部满足。优秀 = 超出预期。

  • 能跑起来：系统能可靠地完成它的工作，现场演示证明这一点。
  • 架构判断力：合理运用上下文、Skill、MCP，以及编排/护栏。
  • 工程严谨度：代码可读、有测试、遵循良好实践。
  • 生产思维：你能清楚讲述自己的评估策略、失效模式，以及规模化之后会变成什么样。

今天的内容直接对应这四行里的两行——架构判断力，以及生产思维。

实验课 · 第5部分 23 — 30
在你自己的毕业项目之前——先来一次有引导的实练

把 EVBot 扩展成一个受监督的小队。

今天不写新的编排代码。五份持久化的子智能体定义，加上正确的提示词，指挥 Claude Code 自己把它们扇出去——这些定义本身就是产出物。

  • 五份子智能体定义，对应第1部分小队里的每一个角色。
  • 由你来指挥 Claude Code 把它们扇出去——和 Claude Code 内部使用的 Task/Agent 模式完全一样。
  • 产出：一张真实的记分卡，对照一个真实的阈值检验，跑在 EVBot 真实的评估数据集上。
实验课 · 第5部分 24 — 30
步骤与检查点

从注册小队到读懂记分卡。

步骤1
阅读五份子智能体定义在跑任何东西之前，先弄懂每个工作者那一项限定工作到底是什么。
步骤2
并行扇出三个工作者指挥 Claude Code 同时运行准确性评分员、依据性检查员和测试运行员。
步骤3
合成记分卡指挥合成员等这三者都完成后，产出一个通过/不通过的裁决。
步骤4
对照阈值检验记分卡有没有闯过发布关卡——如果没有，是哪个工作者标记了什么原因？
步骤5

实验课 · 第5部分 25 — 30
为什么这套方法有效

你刚刚真刀真枪跑了一遍扇出/屏障/合成模式。

三个独立的工作者并发运行，一个屏障步骤等待它们全部完成，然后合成产出一个受关卡把守的 裁决——正是第1部分讲的那个形态，现在已经在一个真实系统上得到了验证，而不再只是 一张图。

你自己毕业项目小队里的一切——不管需要什么角色——都会遵循这同一个形态：独立的工作者、一个同步点、一道关卡。

本课程的最后一次实练

展示它。答辩它。赢得它。

  • 现场演示这个能跑的系统——不是一份讲它会做什么的幻灯片。
  • 讲清楚你在架构、护栏和评估上的选择——并在提问环节为它们辩护。

通过第4部分评分标准的全部四行，就能赢得"Claude Code Builder"认证——超出预期则能拿到优秀评级。

今天，一页讲完

今天改变了什么。

  • 编排意味着有意识地委派——不是什么都需要一整支小队，但真正独立的工作需要。
  • 护栏和评估不是两件孤立的事——它们是证明一个系统安全可上线的两种方法。
  • 你今天把 EVBot 扩展成了一支真正受监督的小队，而不只是读了读这套模式。
  • 毕业项目的每一块拼图——Skill、服务器、编排——现在都握在你手里了。
结课 30 — 30
结语 · 这一周浓缩成一个理念

信任，被验证过。

Skill 打包了一套流程。MCP 给了 Claude 一条实时触达外部世界的通路。但它们单独任何一个， 都无法告诉你合体后的系统是否安全到可以放在真实用户面前。编排决定谁来检查什么。 护栏在最坏的结果发生之前拦住它。评估把"看着没问题"变成一个你能拿出去辩护的数字—— 和一个真实的银行聊天机器人在触达任何一位客户之前所需要的严谨程度一模一样。

  • 有意识地委派，而不是默认就委派。只有当工作真正独立时，一支小队才值得它带来的开销——就是你刚刚在 EVBot 上跑过的那个扇出/屏障/合成的形态。
  • 一道关卡只有在它真能说"不"时才算数。权限、审批步骤，和一个发布阈值——是被强制执行的，不是被建议的。
  • 你现在已经把毕业项目的三块拼图全部握在手里了。第3周的 Skill，第4周的服务器，以及今天的编排、护栏与评估。

扎根解决了 Claude 知道什么。Skill 解决了它能做什么。MCP 解决了它能触达什么。这一周，解决了你到底能不能真正信任它——去把毕业项目建出来吧。
