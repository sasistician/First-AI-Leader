EVBot.

one working system, six components, every decision visible

Today's lecture taught Skills — packaging a recurring procedure so Claude can invoke it without you re-explaining it. EVBot is the vehicle for that lesson, but it's a real, runnable EV Q&A chatbot: every question is checked, routed, retrieved, answered, judged, and safety-checked before it reaches you.

what this deck covers
  • The full pipeline — what runs, in what order, and what can end a request early
  • Guardrails, the router, RAG, the judge, and memory — what each one actually decides
  • The Gradio debug panel and uv — how you'll see and run all of it
  • The judge's rubric, packaged as a Claude Code Skill
  • The six-step lab exercise itself, mapped to what you just learned

Not just that these six pieces exist — why each one is built the way it is.

The Pipeline · One Query, Start To Finish 02 — 10
the whole pipeline, one query at a time

Nine steps run before you see an answer — and two of them can end the request early.

  • 1. Read session memory — recent turns for this session, so pronoun follow-ups resolve correctly.
  • 2. Input guardrail — topic relevance check; off-topic questions exit here, before anything else runs.
  • 3. Router — classifies the query simple vs. complex; a rule-based decision, no LLM call.
  • 4. RAG retrieval — pulls relevant EV documents from the Chroma knowledge base.
  • 5a. Simple path — one answer, from the small model, straight to the output guardrail.
  • 5b. Complex path — two candidate answers, small model and large model, same retrieved context.
  • 6. Judge (complex only) — scores both candidates and picks or merges a winner.
  • 7. Output guardrail — scans the final answer for PII, toxicity, and ungrounded claims.
  • 8. Write session memory — the turn is persisted, and the full trace renders in the debug panel.

Two of these steps are early exits that skip everything downstream — that's deliberate, and it's the throughline for the next two slides.

Guardrails · Before And After Every Answer 03 — 10
what runs before and after every answer

Two guardrails, two different jobs — one keeps bad input from ever reaching the model, the other keeps bad output from ever reaching you.

The input guardrail is a fast, mostly-deterministic keyword pass against EV vocabulary, falling through to a one-shot LLM classification only for ambiguous cases — and it's given conversation history so a follow-up like "how much does it cost?" resolves the pronoun instead of getting flagged as off-topic. The output guardrail bundles three checks: a PII regex scan, a keyword-based toxicity check, and an LLM groundedness check that labels each sentence of the answer SUPPORTED or UNSUPPORTED against the retrieved context.

  • Input guardrail rejects/redirects before router, RAG, or any model call runs — shown as early_exit: true in the debug panel.
  • Output guardrail's groundedness check is what produces the honest "that's not in my knowledge base" fallback instead of a confident-sounding guess.
  • Both guardrails are deterministic-first, LLM-fallback-second — cheap checks run before expensive ones.

A guardrail that can't explain why it blocked something is just a filter. This one shows its reasoning in the debug panel every time.

The Router · Cost, Not Just Capability 04 — 10
deciding which model — and how much process — a query gets

The router's real decision isn't which model answers. It's whether the judge runs at all.

classify_complexity() is rule-based, not an LLM call — word count, comparison keywords ("compare", "vs", "pros and cons"), and multi-model-mention detection. A simple factual question gets one answer from the small, fast model and skips straight to the output guardrail. A complex or comparative question gets two full candidate answers — small model and large model, generated from the same retrieved context — and only then does the judge get invoked to pick between them.

  • Simple path: 1 model call, 0 judge calls.
  • Complex path: 2 model calls, 1 judge call (which is itself another model call).
  • This is a cost/latency lever, not just a quality lever — most questions don't need a second opinion.

Every "complex" query costs roughly 3x the model calls of a "simple" one. The router's job is making sure that cost is paid only when the question actually needs it.

RAG · Where The Answers Come From 05 — 10
where the answers actually come from

The knowledge base is real EV brands, real specs, and deliberately incomplete — the gaps are the assignment, not a bug.

data/ev_docs/ holds real-brand content — Tesla Model 3, Rivian R1T, Ford Mustang Mach-E, Chevy Bolt, Hyundai Ioniq 5 — across model specs, charging, incentives, and battery/maintenance, each explicitly dated and marked illustrative rather than presented as live pricing. Ingestion (evbot/rag/ingest.py) hand-chunks the markdown, embeds it locally via Chroma's bundled ONNX model (no external embeddings API key), and rebuilds the collection idempotently every run.

  • No web search in this pass — RAG-only, on purpose, so the retrieval step is easy to reason about.
  • EV insurance costs are missing from the KB entirely — that gap is what Step 4 of the lab exercise is built to surface.
  • Retrieval depth (k) is larger for complex/comparative queries than simple ones — a comparative question needs more chunks to ground both vehicles being compared.

An incomplete knowledge base isn't a flaw to hide — paired with the output guardrail's groundedness check, it's what makes "I don't know" a visible, correct behavior instead of a silent failure.

LLM-As-Judge · Scoring, Not Generating 06 — 10
judging quality, not generating it

The judge never writes the answer. Its only job is deciding which of two candidates deserves to reach you.

For complex queries, judge.py sends both candidate answers — grounded in the identical retrieved context — to the larger local model with a four-criteria rubric: Accuracy, Completeness, Groundedness, Clarity, each scored 1-5. The judge then applies a decision policy: a clear winner, or a merge of the strongest parts of both, plus a rationale explaining the call.

  • Same retrieved context for both candidates — the judge is comparing model quality, not comparing who got better information.
  • Output is a JudgeResult: winner, merged answer, rationale, and the full score breakdown — all visible in the debug panel.
  • The judge itself runs on the larger, more capable model — judging is treated as harder than answering.

This is the piece of EVBot packaged as a Claude Code Skill later in this deck — a rubric worth invoking standalone, not just buried in one file.

Memory · Two Systems, Two Jobs 07 — 10
two systems named "memory," doing two different jobs

Session memory remembers your conversation. The knowledge base remembers the world. Conflating them breaks both.

evbot/memory.py is a SQLite-backed conversation log — append_turn and get_recent_turns — that persists across app restarts and is read at the start of every turn so pronoun follow-ups resolve correctly. It is architecturally distinct from the Chroma knowledge base RAG draws from at the retrieval step: one changes every conversation, the other only changes when someone ingests a new document.

  • Session memory: per-session, keeps growing, survives restarts, has nothing to do with EV facts.
  • Knowledge base: shared across all sessions, only changes on re-ingestion, has nothing to do with who's asking.
  • Step 5 of the lab exercise tests this directly: restart the app mid-conversation and confirm memory survives while the KB stays exactly the same.

If these two lived in one table, adding an EV document would look like "the bot learned something from talking to you" — which is not what happened, and would make debugging much harder.

The UI And The Environment 08 — 10
what you can see, and what runs underneath

A second panel exists specifically so nothing about this system is a black box.

app.py builds a Gradio gr.Blocks interface — deliberately not the higher-level ChatInterface — because it needs a second "under the hood" panel next to the chat pane, rendering the full trace of every turn: guardrail verdicts, the router's decision, retrieved chunks, candidate answer(s), judge scores and rationale when the judge ran, and memory reads/writes. Underneath all of it, uv manages the Python environment — pyproject.toml plus a committed uv.lock — the first use of uv in this course.

  • The debug panel is not cosmetic — every checkpoint in the lab exercise is "confirm the debug panel shows X."
  • gr.Blocks over ChatInterface is a deliberate trade: more code, but full control over that second panel.
  • uv run pytest, uv run python -m evbot.rag.ingest, uv run python -m evbot.app — the same environment, three different entry points.

Inspectability was a hard requirement for this lab, not an afterthought — you should never have to guess which component made a given decision.

Back To This Week's Actual Lesson 09 — 10
back to this week's actual lesson

The judge's rubric is the one piece of EVBot genuinely worth packaging as a Skill — here's why the guardrail isn't.

.claude/skills/answer-quality-judge/SKILL.md packages the judge's four-criteria rubric and decision policy as an invokable Skill — its frontmatter description fires on prompts like "score these two draft answers" or "which response is better," and its field names mirror judge.py's RUBRIC_PROMPT exactly. The input/output guardrails were deliberately not packaged this way: they're cheap, deterministic, inline checks built for latency, not a multi-criteria judgment call worth invoking standalone outside the app.

  • Same test from this week's lecture: does it recur across contexts, is it a judgment call (not mechanical), can it be stated in one sentence, does getting it wrong cost something — the judge rubric clears all four, the guardrail's keyword scan doesn't need to.
  • Step 6 of the lab exercise has you diff SKILL.md against judge.py's rubric and then invoke the Skill directly in a Claude Code session on two pasted answers.

The whole app runs the rubric already. The Skill exists so you can run the exact same judgment on any two answers, anywhere, without opening judge.py at all.

The Lab Exercise · Six Steps, Six Checkpoints 10 — 10
what you'll actually do, step by step

Six steps, six checkpoints — each one designed to make a specific architectural decision visible in the debug panel.

  • 1. Simple, in-KB question — confirm the judge is null; the router skipped it.
  • 2. Off-topic question — confirm early_exit: true; router/RAG/judge never ran.
  • 3. Genuinely comparative question — confirm both candidate answers appear, and read the judge's rationale.
  • 4. A question the KB doesn't cover (EV insurance costs) — confirm the honest "not in my knowledge base" fallback, not a guess.
  • 5. Two-turn pronoun follow-up, then restart the app — confirm memory survives the restart while the KB doesn't change.
  • 6. Open SKILL.md next to judge.py — confirm the matching rubric, then invoke the Skill directly on two pasted answers.

Every checkpoint above maps to a slide in this deck — if a checkpoint doesn't behave the way its slide predicted, that's the debugging exercise, not a distraction from it.
