Recap · From Week 1 02 — 21
before today

Last week was about the loop. This week is about what's in it.

You learned to direct Claude Code through perceive → plan → act → observe, across permission modes, on real, messy code. The loop worked — but you've probably already noticed something: point that same loop at two different projects and you get wildly different quality of output. Sometimes Claude "just gets it." Sometimes you're re-explaining the same conventions every single session.

  • The loop is the mechanism. It runs the same way regardless of project.
  • What changes is what the model has to work with when it runs.
  • Today's question: what determines whether a session starts grounded or starts guessing?

That answer is context engineering — and it's the difference between a tool that fights you and one that already knows your world.

The Problem · Part 1 of 3 03 — 21
what fills the gap when you don't

Garbage in, plausible garbage out.

When you ask a vague question, the model doesn't pause to ask what you meant — it fills the gap with the most statistically common pattern it has seen for requests like yours. That pattern is often reasonable in general, and wrong for your specific codebase.

Without context "Add a retry to the payment call." Result: a generic exponential backoff, no idempotency key, ignoring the project's existing retryWithBackoff() helper — and a real risk of double-charging a customer on retry.
With context Same prompt, grounded by a CLAUDE.md CLAUDE.md already documents the retry helper and the idempotency requirement. Result: correct integration, first try — no double-charge risk, no re-explaining.

The model isn't broken. The grounding is missing.

The Problem · Part 1 of 3 04 — 21
every token competes for attention

Context is a budget, not a wishlist.

Every model has a finite context window. Everything that goes into it — system instructions, conversation history, file contents, retrieved docs — shares that same budget and competes for the model's attention. Padding the window with irrelevant material doesn't just waste space; it dilutes the signal, even when everything technically "fits."

~8% Grounding
~35% Conversation history
~32% Retrieved docs
~25% Output headroom
Grounding — CLAUDE.md, system instructions. Small, fixed, non-negotiable.
Conversation — grows every turn, whether or not it's still relevant.
Retrieved docs — pulled in on demand. The lever you actually control.
Headroom — must stay free for the model's own output.

Illustrative split for a typical session — actual proportions shift task to task.

Attention is the model's scarcest resource — not tokens.

The Problem · Part 1 of 3 05 — 21
a plausible answer isn't a correct one

It doesn't refuse. It guesses — confidently.

When context is missing, the model doesn't throw an error or say "I don't know your conventions." It produces something fluent, plausible, and quietly wrong — which is more dangerous than an obvious failure, because it passes a skim review.

a quietly wrong guess

Claude added a new field to an API response. The naming matched the file's existing conventions perfectly. It also silently broke three downstream consumers nobody had mentioned — because nothing in the project said they existed.

The fix isn't a better prompt. It's better grounding — and there are three layers of it.

Three Layers · Part 2 of 3 06 — 21
one layer per kind of knowledge

Three different problems. Three different layers.

CLAUDE.md, memory, and RAG all answer the same question — "how does the model know what it needs to know?" — but each is built for a different shape of problem. Reach for the wrong one, and you've wasted the layer that should have handled it.

CLAUDE.md / AGENTS.md
Static project grounding Loaded every session, identical every time.
Best for Conventions, architecture notes, "don't do X."
always present, same content every time
Memory
Persistent facts across sessions Accumulates as you work together.
Best for Decisions made, preferences learned, corrections given once.
grows over time; survives a fresh session
RAG
Dynamic retrieval at query time Pulled in only when relevant.
Best for Large or changing corpora — codebases, docs, tickets — too big for any context window.
different content every query, fetched on demand

Get the layer right, and you stop paying the cost of the others.

CLAUDE.md, Up Close · Part 2 of 3 07 — 21
the file claude reads before anything else

One file, read at the start of every session.

CLAUDE.md isn't documentation for humans — it's the first thing the model reads, before it touches your code. What you put in it, it never has to be told twice.

01Project overview
What goes here

One paragraph: what the project does, who uses it, the stack.

Why it matters

Orients a cold session in seconds, not several exploratory reads.

02Conventions
What goes here

Naming, formatting, file layout, the helpers that already exist.

Why it matters

So they don't get silently reinvented in a new function.

03Do / don't
What goes here

Explicit guardrails — "never edit generated files," "run X before committing."

Why it matters

Rules a teammate absorbs by osmosis; the model needs them stated.

04Architecture notes
What goes here

Decisions no single file shows — why the retry helper exists, why two similar services stay separate.

Why it matters

Without it, a "cleanup" can quietly undo a deliberate choice.

05Build / test commands
What goes here

The exact commands to run — lint, test, build, deploy.

Why it matters

So the agent verifies its own work instead of guessing.

If you've explained it more than once, it belongs in CLAUDE.md.

Memory, Up Close · Part 2 of 3 08 — 21
what's worth remembering, on purpose

What should survive when the session ends?

CLAUDE.md is static — written once, identical every session. Memory is different: it accumulates, and how you organize it is up to you. Below is one workable taxonomy — not a schema Claude Code enforces, just a pattern worth copying.

01User
What it captures

Your role, preferences, how you like to work.

Example

"Prefers terse responses, reviews every diff before merging."

02Feedback
What it captures

Corrections and confirmations — what to avoid, what worked.

Example

"Don't mock the DB in integration tests — past incident."

03Project
What it captures

Decisions, deadlines, ongoing context not visible in the code itself.

Example

"Auth rewrite is compliance-driven, not cleanup — scope accordingly."

04Reference
What it captures

Pointers to where the real, up-to-date answer lives externally.

Example

"Bugs are tracked in Linear project INGEST, not GitHub Issues."

Memory isn't a transcript of every conversation — it's the small number of facts worth never re-explaining.

RAG, Up Close · Part 2 of 3 09 — 21
retrieval, not memorization

Some corpora are simply too large to hand over — so don't.

A 200-file codebase, a wiki with five years of decisions, a support-ticket archive — none of it fits in a context window, and most of it is irrelevant to any single question. RAG's job is to fetch only the slice that's actually relevant, right when it's needed.

Step 1 Chunk & embed Break docs into pieces, convert each piece into a vector that captures its meaning.
→
Step 2 Store Index those vectors so the closest matches to any new question can be found fast.
→
Step 3 Retrieve Find the chunks closest in meaning to the current question.
→
Step 4 Augment Drop just those chunks into context, right before the model answers.

CLAUDE.md and memory are things the model always has. RAG is something it asks for, on demand.

Choosing the Right Layer · Part 2 of 3 10 — 21
match the layer to the problem's shape

A simple test: how often does it change, and how big is it?

Stable fact
→ CLAUDE.md Rarely changes, small. "We use pnpm, not npm." "Tests live in /tests, mirroring /src."
Durable decision
→ Memory Accumulates over time. "We rejected GraphQL last quarter — see ADR-012." "This user wants PR descriptions, not inline comments."
Large / changing corpus
→ RAG Too big to hold, keeps growing. The full codebase. The support-ticket history. The product wiki.

Most projects need all three. Most context debt comes from skipping one.

Context Debt · Part 3 of 3 11 — 21
the debt that accrues in silence

Context debt is tech debt's quieter cousin.

Tech debt is code that works but costs more every time you touch it. Context debt is the same idea, one layer up: the gap between what your agent actually needs to know to do good work, and what's actually grounded in CLAUDE.md, memory, and retrievable docs. It doesn't show up as a failing test. It shows up as every session starting a little more confused than it should.

  • You explain the same convention to Claude for the third time this month.
  • It confidently violates a rule that exists — just nowhere it could see.
  • "It worked differently last week" — with no record of what changed or why.
  • A new teammate, human or agent, takes days to get productive, because nothing is written down.

Like tech debt, it compounds silently — until a session goes badly enough that you notice.

Anatomy of Context Debt · Part 3 of 3 12 — 21
five familiar failure modes

Five ways it shows up.

01Missing CLAUDE.md
What it looks like

No grounding file, or three sentences from a year-old README.

The cost

Every session starts from zero; conventions get re-explained or re-guessed.

02Stale memory
What it looks like

Saved facts that were true once, but the project has since moved past.

The cost

Confidently wrong answers that cite a decision already reversed.

03No examples
What it looks like

Rules stated abstractly — "follow our conventions" — nothing concrete to match.

The cost

The model interprets the rule its own way — plausibly, rarely correctly.

04Conflicting instructions
What it looks like

CLAUDE.md says one thing, a code comment another, memory a third.

The cost

The model picks one silently; you find out which only when it breaks.

05Ungrounded RAG corpus
What it looks like

A retrieval index built once, never refreshed, pointing at superseded docs.

The cost

Retrieval "succeeds" — it returns confident, well-formatted, outdated answers.

None of these are exotic. All five are common — and each one, on its own, is fixable faster than you'd expect.

Lab Walkthrough · Step 1 of 4 15 — 21
read it cold, before writing anything

Read Ledger cold — like Claude would.

Before writing anything, audit it: open the repo fresh, with no prior knowledge, and try to answer "what would I need to know to safely change this code?" Note every place you guessed, assumed, or had to dig through git history or Slack to find out.

from ledger

The payment retry logic has no comment explaining its idempotency-key requirement. The only place that's ever been written down is a six-month-old Slack thread.

Whatever you just struggled to find — that's the actual audit. Context debt isn't abstract once you're staring at it.

Lab Walkthrough · Step 2 of 4 16 — 21
be ruthless about what's load-bearing

Write down only what you'd have to explain twice.

Turn the audit into a CLAUDE.md. The temptation is to document everything — resist it. A ten-page CLAUDE.md is its own kind of context debt; it eats the same budget you saw in Part 1. Keep to the five sections from earlier — overview, conventions, do/don't, architecture notes, test commands — and be ruthless about what's actually load-bearing.

from ledger

The idempotency-key convention from Step 1 becomes one line under "do / don't": "Never call the payment gateway without an idempotency key — see PaymentClient.charge()."

Good grounding is short. That's not a constraint — it's the point.

Lab Walkthrough · Step 3 of 4 17 — 21
what's true now, not what's always true

Capture the one decision that isn't in any file.

CLAUDE.md covers what's always true. Memory covers what's true now, learned along the way. Today: find one durable decision buried in Slack or institutional memory — like "we decided not to support partial refunds in v1" — and save it as a project memory, so the next person, or the next session, doesn't have to rediscover it the hard way.

from ledger

"Partial refunds deferred from v1 (Slack, March). Reintroducing this needs product sign-off, not just an engineering fix." One sentence, saved once, never re-litigated.

A memory entry is cheap to write and expensive to lose.

Lab Walkthrough · Step 4 of 4 18 — 21
close the loop

Same question, asked twice. Compare the answers.

Point Claude at Ledger's existing /docs folder, then ask the same real question you'd ask about this service — before any grounding existed, and after.

Before grounding "Can I safely add partial refunds to Ledger?" A generic implementation sketch, no awareness it was already deliberately deferred — quietly reopens a closed decision.
After grounding Same question, same service Correctly surfaces the memory entry — "deferred from v1, needs product sign-off" — instead of treating it as a clean-slate feature request.

That difference is everything you just built, made visible in one diff of answers.
