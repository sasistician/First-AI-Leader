回顾与桥接 · 来自第2周 02 — 24
在今天之前

你已经让 Claude 扎根于你的项目是什么。但这不等于它该怎么去处理它。

上周你给 Ledger 配置了一份 CLAUDE.md、第一条记忆条目，以及一个指向自身文档的指引——这些都是关于项目的、能跨会话持续存在的稳定事实。这就是扎根，而且它确实管用：同一个问题，扎根前后各问一次，第二次的答案好得判若两人。但扎根是「事实形状」的。它回答的是「这个代码库里什么是真的」。它回答不了「我们每次做X都遵循的这五步流程是什么」——那是「流程形状」的问题，上周学的东西一个都没有把它打包起来。

  • CLAUDE.md 和记忆保存的是静态或变化缓慢的事实——约定、决策，以及指向真正答案所在位置的指引。
  • 一个反复出现的任务是一套流程——一连串需要判断的决定，不是一个说一次就完事的事实。
  • 每次这个任务出现，总有人要在提示词里从零重新解释一遍这套流程，全凭记忆，还得祈祷自己没漏掉任何一步。

扎根解决了 Claude 对你的世界知道什么。它从来没解决那件你一直在重复打字的事。

问题所在 · 第1部分 03 — 24
一个真实项目，不是假设案例

三名工程师，同一个 Ledger 退款修复，三套不同的流程。

Ledger——上周已经扎根——现在需要一个新的退款原因代码。这是一套五步流程：检查幂等键处理、按公司格式在审计日志里追加一条记录、发布到 billing-events 主题、扩展退款状态枚举，并针对沙箱支付服务商加一个集成测试。这套流程本身没什么不清楚的地方。 它甚至写在一份 wiki 页面里——只是没人会在冲刺进行到一半时打开它看。但它不是关于 Ledger 的一个事实——它是你对 Ledger 做的一件事——所以它从没被写进 CLAUDE.md，而是由三名不同的工程师，每次都用自己的话、凭着记忆，重新跟 Claude 解释一遍。

  • 工程师 A 写了一段仔细的五步提示词。干净利落地上线了。
  • 工程师 B 只记得五步里的四步。上线时漏了沙箱集成测试——直到沙箱合约发生变化之前，没人注意到。
  • 工程师 C 压根不知道这套流程存在，只是让 Claude「随便加个退款代码」。Claude 做了一件看起来合理的事。但它还是错的。

这套流程本身从来都不是难点。难的是让它每次都被以同样的方式执行，而不需要任何人重新打一遍字。

什么是 Skill？· 第1部分 04 — 24
缺失的那层打包

Skill，就是一套 Claude 能自己找到、加载并遵循的流程。

具体来说：一个文件夹，里面有一份 SKILL.md 文件——frontmatter（name 加 description）加上 具体步骤——外加可选的打包脚本或参考文档。Claude 读取你当前的任务，拿它去比对每一个 Skill 的 description， 如果有一个匹配，就加载它、遵循它。下一次，没人需要重新解释退款代码流程；它就是一个文件， Claude 会自己去把它取来。

  • 它是一个文件，不是一种习惯。 可以像其他代码一样被版本管理、审查、共享——不是只活在某一个工程师的提示词历史里的东西。
  • 它是可被发现的，不是被硬塞进去的。 Claude 根据 description 判断相关性；不相关的任务永远不会加载它，也永远不用为它付出上下文代价。
  • 它是判断，不是一个宏。 Claude 会阅读并遵循这些步骤，根据眼前的具体情况去调整——就像一个称职的工程师遵循一份操作手册的方式，而不是逐字节机械执行。

这跟把一段重复代码提取成一个命名恰当的函数是同一个动作——只不过决定何时调用它的「调用者」是 Claude，靠的是判断而不是一个固定条件，而且步骤本身在每次调用时都会被重新调整，不像函数那样逐字节原样重放。

谱系 · 第1部分 05 — 24
交接一套流程的四种方式

提示词、脚本、Skill、子智能体——同一个目标，四种不同的取舍。

在动手构建之前，值得先精确搞清楚 Skill 到底替代了什么——以及它没有替代什么。

01提示词
是什么

一句一次性的自然语言指令，可能是现场打出来的，也可能是从文档、Slack 讨论或自己的记忆里复制粘贴过来的。

复用性实际来自哪里

没有——你自己就是那层打包。只要你忘了一步，或者不是你在敲提示词，这套流程就不会发生。

02脚本
是什么

确定性的代码，执行一套固定流程，不带任何判断。

复用性实际来自哪里

对它当初被写来处理的那个具体场景，复用性很高；任务稍有变化，复用性就归零——而且你还得知道它存在，并亲自去运行它。

03Skill
是什么

一套被打包起来的流程（SKILL.md 加上可选的脚本/资源），由 Claude 自己发现、并凭判断去遵循。

复用性实际来自哪里

只写一次，只要任务与它的 description 匹配就会自动触发——跨会话、跨项目、跨团队成员都成立。

04子智能体
是什么

一次独立的、被委派出去的智能体调用，拥有自己的上下文和工具，被派去完成一块有边界的工作，然后汇报结果。

复用性实际来自哪里

智能体的 类型 是可复用的（比如「code-reviewer」），但每一次调用都是一个全新、独立的委派工作单元——不是一份共享的操作方案。

注意这个规律：复用性从提示词到 Skill 一路攀升。但「更自主」和「更可复用」不是同一根坐标轴——把这两者混为一谈，正是误用的开始。下一页详细说。

谱系 · 第2部分 06 — 24
自主性和复用性不是同一根坐标轴

Skill 和子智能体都会用到判断。它们的区别在于「委派」，不在于用了多少判断。

接下来自然会有的疑问：Skill 不就是个小号的子智能体吗？不是。Skill 运行在你当前的智能体内部， 在你当前的这次会话里——它临时扩展了这个智能体懂得怎么做的事，然后会话会原样接着往下走。子智能体 则完全是另一次调用：拥有自己的上下文窗口、自己的工具权限，而且它是汇报结果，不会融入你当前的 对话。当你想让你正在对话的这个智能体去完成任务、只是遵循一套已知有效的流程时，用 Skill。 当你想把工作隔离开来——需要独立的上下文预算、可以并行处理，或者不想让它搅乱主会话——时，用子智能体。

1 提示词 复用性存在于你的记忆里。忘了，就没了。
→
2 脚本 复用性存在于固定的代码里。可靠——直到任务稍有变化。
→
3 Skill 复用性存在于一套 Claude 自己能发现、自己能遵循的流程里。
→
4 子智能体 复用性存在于一个被委派的角色里，不是一份共享方案——这是另一根坐标轴，不是在这根轴上更进一步。

这周真正要紧的边界，是提示词、脚本和 Skill 之间的区别。子智能体会有专属的一周来讲——现在，只要别把「能自己跑」误当成「能力更强」就行。

Skill 的解剖 · 第2部分 07 — 24
两个字段决定一个 skill 到底会不会触发

frontmatter——name 和 description——就是全部的发现面。文件里其余的一切，在它匹配之前都是不可见的。

SKILL.md 开头是一段 YAML frontmatter——两个字段，name 和 description，这个区块里没有别的东西。 这不是格式上的偶然：这是 Claude 在判断一个 Skill 是否相关之前，唯一会读的那部分文件。 每一个已安装 Skill 的 frontmatter，每次都会被拿去和你当前的任务比对，不管它最后有没有被用到。 底下的步骤在匹配发生之前不会被加载。description 写得含糊，一个真正有用的 Skill 就永远不会触发； 写得精确，它就会在该触发的时候准确触发，其余时候保持沉默。

示意用途，非真实文件 
---
name: ledger-refund-code
description: Add a new refund reason code to Ledger — idempotency check,
  audit-log entry, billing-events publish, refund-state enum extension, and a
  sandbox integration test. Use when adding or changing refund reason codes.
---
  • name——一个简短的标识符。用于在日志里识别这个 Skill，也方便你直接引用它——真正承担匹配重活的是 description；name 只是一个与它对应的简短标识。
  • description——Claude 用来判断相关性的唯一字段。它必须同时说清楚这个 Skill 做什么、以及什么时候该用它——光有个标题，不会在正确的任务上触发匹配。
  • frontmatter 以下的所有内容——步骤、打包的脚本、参考文档——对匹配这一步来说都是死重。在 description 完成它的工作之前，这些内容一个字都不会被读。

一个 description 写得薄弱的 Skill，实质上根本不算 Skill——它只是一个 Claude 永远不会打开的文件夹。

Skill 的解剖 · 第2部分 08 — 24
为什么 skill.md 要保持精简

SKILL.md 是一份索引，不是一本参考手册。细节住在一跳之外，只有流程真正需要时才会被加载。

一旦一个 Skill 匹配成功，它的 SKILL.md 就会被加载进上下文——但这不代表它可能用到的一切都该写在文件里面。 一个打包了真正详尽流程的 Skill——一整套设计系统、一批代码模板、一份风格指南——可能会把 SKILL.md 撑成一大堵文字墙，Claude 每一次调用都得扛着它，而其中大部分内容跟今天的任务毫不相关。解决办法， 和拆分一个臃肿模块成一份索引加若干专注文件是同一种纪律：SKILL.md 保持简短的步骤和指引；沉重的 参考材料活在独立的文件里，只有某个具体步骤真正用到时才会被读取。

  • Frontmatter 会为每一个已安装的 Skill 加载，每次任务进来都是如此——它必须保持轻量。
  • SKILL.md 的正文只在匹配发生后才加载——依然保持轻量：只有步骤和指引，不是参考材料本身。
  • 打包的资源文件只在当前正在执行的步骤真正需要那部分细节时才会加载——不是一次性全部加载，也不是每次调用都加载。

这跟惰性导入（lazy import）是同一种直觉：只加载当前这一行真正需要的东西，而不是把整个库都先加载进来以防万一。

Skill 的解剖 · 第2部分 09 — 24
一个真实的 skill，不是玩具示例

这份讲义背后的那个 Skill——真的是它。

你在这门课上见过的每一份讲义——从第0周到这一份——都是用一个真实存在、已经安装好的 Skill 生成的， 它叫 frontend-slides：它能根据一份文字大纲，构建出动画丰富的 HTML 演示文稿。它不是为这堂课 特制的样品。它是那个真正把一份大纲变成你屏幕上这份讲义的文件夹。接下来两页会直接引用它—— 它的 frontmatter、它自己陈述的一条原则，以及它选择延后加载、而不是全部内联进去的四个资源文件。

  • 它的 name 和 description——为了让它能够触发，必须匹配上「帮我做一份演示文稿」这句话的那些确切文字。
  • 它自己陈述的核心原则——其中一条，它用自己的话，命名为渐进式披露。
  • 它的四个资源文件——html-template.md、animation-patterns.md、STYLE_PRESETS.md、viewport-base.css——在需要它们的阶段到来之前，一个都不会被加载。

如果你一直对这些讲义的样子有点小小的惊喜，那份惊喜其实是被设计进了一个 Skill 文件里，不是每周重新敲出来的。

Skill 的解剖 · 第2部分 10 — 24
这个文件，用它自己的话

先读 frontmatter——然后看着它把渐进式披露列为自己的规则之一。

以下两段摘录，逐字复制自真实的 SKILL.md。

引用1 · SKILL.md 第1-4行，逐字摘录 
---
name: frontend-slides
description: Create stunning, animation-rich HTML presentations from scratch or by converting PowerPoint files. Use when the user wants to build a presentation, convert a PPT/PPTX to web, or create slides for a talk/pitch. Helps non-designers discover their aesthetic through visual exploration rather than abstract choices.
---

这就是两页之前提到的完整发现面。注意它同时说明了是什么——「stunning, animation-rich HTML presentations... or by converting PowerPoint files」——和什么时候用——「Use when the user wants to build a presentation, convert a PPT/PPTX to web, or create slides for a talk/pitch」。恰好是一个 description 需要的那两件事，不多也不少。

引用2 · 第4/5条核心原则 · SKILL.md 第15行，逐字摘录 
4. **Progressive Disclosure** — Read lightweight style indexes first. For bold
templates, use small preview cards for style previews and load the full
`design.md` only after the user picks that template.

这个 Skill 用自己的话陈述了幻灯片8里的那条原则，把它列为五条编号核心原则中的一条——并给出了一个具体实例：在用户真正选定某个模板之前，不要加载沉重的 design.md 文件。

注意这两段摘录里缺了什么：没有真正的 HTML，没有动画代码，没有配色方案。那些东西活在别处——下一页揭晓。

Skill 的解剖 · 第2部分 11 — 24
SKILL.md 没有承载的那些细节

十个文件里的四个，装着 SKILL.md 延后处理的所有内容——而这份真实的表格，精确写明了每一个文件分别在什么时候被读取。

frontend-slides 在它的 SKILL.md 旁边打包了若干资源文件。它们的内容都没有内联写在 主文件里——SKILL.md 只是给每一个文件命名、说明它的用途，并说明流程的哪个阶段真正需要它。这是 渐进式披露被实践出来，而不只是被陈述出来：下面这张表逐字复制自这个 Skill 自己的「Supporting Files」 章节（SKILL.md 第369-377行，十行里的四行——另外六行涉及一个大胆风格模板子包和一些实用脚本， 不在本次讨论范围内）。

  • viewport-base.css（133行）——真正强制使用的 CSS，要求整段粘贴进去：固定的1920×1080舞台、幻灯片可见性规则、缩放变换的约定。SKILL.md 并不描述这段 CSS，它只是说明要把它的全部内容包含进去。

构建你自己的 · 第3部分 · 第1步（共4步） 12 — 24
第1步（共4步）· 在你写下第一行 skill.md 之前

不是每一个反复出现的任务都天生适合做成 Skill。先用这份清单检验一下候选任务。

构建一个 Skill 是实打实的工作：description 必须精确，步骤必须能泛化，而且——往往——还要组织好 资源文件。把这份精力花在一个错误的候选任务上，你会得到两种失败之一：一份本该由脚本做的工作， 却披上了 Skill 的开销；或者一个模糊到任何 description 都不可能可靠触发它的任务。第1部分里那套 退款原因代码的流程，把下面每一项检查都过了。这不是巧合——这正是这门课反复拿它做例子的原因。

  • 它会反复出现，而且不只是对你一个人。 如果只有你一个人会碰到这个任务，一句写得好的一次性提示词，比一个 Skill 更划算。
  • 它是一连串步骤，不是一个单一的事实。 一个事实——「审计日志用的是公司格式X」——该放进 CLAUDE.md，不是 Skill。Skill 存在的意义，是给那些不止一步的流程用的。
  • 它需要把判断施加到这些步骤上，而不是完全一致的机械执行。 如果每一份输入都会产生完全相同、零调整的输出，就写个脚本——在那个具体场景下它会比 Skill 更可靠（见幻灯片5的对比表）。一个 Skill 值得存在，是因为这些步骤必须被阅读、并根据眼前的实际情况去调整。
  • 你能用一句话说清楚它是什么、以及什么时候该用它。 如果你连这么精炼地概括这个任务都很吃力，那说明你对这个模式的理解还不足以把它打包——或者它其实悄悄是两个任务共用了一个名字。（下一页整页都在讲这个。）
  • 做错了会有真实、能被察觉的代价。 如果没人会在意某一步被跳过了，那它就不值得被打包。

五项检查，一个候选任务：Ledger 的退款代码流程五项全过。过四项或五项，值得构建。只过一两项， 你通常发现的其实是一个脚本、一条 CLAUDE.md 事实，或者一个还没被理解到足以打包的任务。

构建你自己的 · 第3部分 · 第2步（共4步） 13 — 24
第2步（共4步）· claude 在做决定之前唯一会读的那一行

在写下第一个步骤之前，先写 description——它是这份文件里唯一能决定其余部分是否会被执行的那一部分。

幻灯片7已经说明了 description 就是全部的发现面。知道这一点，不代表写起来就容易——大多数 写得不好的 description，会以两种特定方式之一失败，而这两种失败在你实际使用之前都看不出问题。 下面：同一个 ledger-refund-code Skill，用三种不同的方式描述。

Description

「处理退款代码。」

结果

永远不会触发。

原因

泛泛的动词，没有触发条件，没有区分性细节。它没有描述任何足够具体、可供匹配的东西——所以它什么都匹配不上。

Description

「更新 Ledger 的计费系统。」

结果

会误触发。

原因

范围太宽。它读起来也像是能匹配上其他不相关的计费任务——一次定价调整、一个计费仪表盘的修复——而这些任务完全不需要那五个步骤。一个在错误任务上触发的 Skill，跟一个永远不触发的 Skill 一样糟糕。

Description
回调 · 幻灯片7示意性 frontmatter 的逐字引用

"Add a new refund reason code to Ledger — idempotency check, audit-log entry, billing-events publish, refund-state enum extension, and a sandbox integration test. Use when adding or changing refund reason codes."

结果

可靠触发。

原因

同时说明了是什么（那五个具体步骤）和什么时候（那个精确短语——「adding or changing refund reason codes」——而不是泛泛的「billing」）。这就是幻灯片7那段示意性 frontmatter 的逐字引用。

  • 用你团队实际会说出口、用来请求这件事的那些词，而不是你自己意图的转述——Claude 匹配的是打出来的请求本身，不是你心里想的意思。
  • 把「什么时候」明确说出来。一个好 Skill 永远不触发，最常见的原因就是 description 只说了它做什么，却把触发条件留在了字里行间没写明。
  • 把边界写得跟内容一样用心——一个 description 应该把相邻的任务排除在外，而不只是把目标任务包括进来。
  • 在信任它之前，拿2-3个相邻任务去测试一下：这个 description 会不会也貌似能匹配上一些它本不该匹配的东西？

description 是和 Claude 的匹配过程之间的一份合约，不是写给人类读者看的注释——把它写成那种会决定 它下面的函数到底会不会被执行的文档字符串（docstring）。

构建你自己的 · 第3部分 · 第3步（共4步） 14 — 24
第3步（共4步）· 让索引保持精简

一旦 description 触发成功，别让 SKILL.md 本身变成一堵文字墙，白白抵消这份胜利。

这跟幻灯片8的纪律是同一条，现在变成了一个构建步骤，而不只是一条原则。 frontend-slides 就是这条纪律在真实规模下依然成立的证明：SKILL.md 保持为一份380行的 步骤与命名原则索引；STYLE_PRESETS.md、viewport-base.css、html-template.md 和 animation-patterns.md 加起来的939行——也就是两页之前那张 Supporting Files 表——都活在 它之外，只在需要的阶段被读取。构建你自己的 Skill，意味着在你流程里的某一步需要超过几行参考 材料的那一刻，做出同样的判断。

  • 先把你流程的步骤列成 SKILL.md 里一份简短的编号清单。这份清单就是索引——不是用来同时承载一份 schema、一整份风格指南，或一个很长的枚举的地方。
  • 一旦某一步需要超过几行参考材料，就把它拆进一个独立的文件——这正是 frontend-slides 所做的事：把风格选择放进 STYLE_PRESETS.md，把 HTML 样板代码放进 html-template.md，而不是把它们内联进 SKILL.md。
  • 像 frontend-slides 在它自己的 Supporting Files 表里那样，从 SKILL.md 里引用每一个拆分出去的文件：写出它的名字，说明它的用途，说明哪一步会读取它。
  • 不是所有东西都该放进资源文件——如果某段内容不管走哪条路径、每一次调用都需要用到，就把它内联写进去。渐进式披露只在材料的使用取决于流程走哪个分支时才划算。

SKILL.md 是索引；资源文件是书库。frontend-slides 证明了这种拆分在总共1300多行的规模下 依然成立——同一条纪律，缩小到一个只有一个参考文件的五步退款代码流程时，一样干净利落地适用。

构建你自己的 · 第3部分 · 第4步（共4步） 15 — 24
第4步（共4步）· 一份 skill.md 在被验证之前，只是一个文件夹

一个没测试过的 Skill 还配不上这个名字——它只是一个可能会触发的文件夹。

写完 SKILL.md 不代表它真的能用。「测试一个 Skill」不是单元测试——而是拿真实、没有事先 写好脚本的请求去运行它，用你团队实际说话的方式去表达，然后观察两端各自发生了什么：它该触发 的时候有没有触发，它不该触发的时候有没有保持沉默。

  • 用自然的表达方式，在真实任务上运行它。 像工程师 C 那样去请求这个改动——「随便加个退款代码」——而不是用你写 description 时的措辞。如果它在自然表达上不触发，说明 description 还没匹配上现实。
  • 检查它到底有没有触发。 沉默就是 description 的失败——回去看幻灯片13的规则：「什么时候」写明确了吗？用的是人们实际会用的词吗？
  • 检查它有没有在错误的任务上触发。 试试2-3个用词相近的相邻任务——一次泛泛的计费修复、一个不相关的审计日志改动——确认它在这些任务上都保持沉默。
  • 观察它加载之后做了什么，不只是它有没有加载。 它有没有按顺序遵循步骤？它有没有在正确的阶段才去取用资源文件，还是一股脑全部提前加载？一个含糊的步骤，就是它会瞎发挥、发挥错的地方。
  • 收紧后重新运行——不要从头重写。 大多数修复都很局部：补上缺失的触发短语，把一个游离的资源文件拆出去，把某个含糊的步骤写得更锋利一点。然后再跑一遍同样的检查。

上线一个 Skill，要像上线任何其他「自己决定何时运行」的代码一样：证明它该触发时会触发，不该触发时 会沉默，而且做的是对的事——然后才让你的团队依赖它。

发现与调用 · 第4部分 · 第1步（共4步） 16 — 24
一个任务，所有已安装的 skill，一次匹配过程

发现不是针对某一个 Skill 的查表操作。它是同时针对每一个已安装 Skill 做出的一次判断。

幻灯片7说明了每一个已安装 Skill 的 frontmatter 都会被拿去和你当前的任务比对。这在实际操作中的 样子是：没有优先级顺序，没有「先匹配先赢」，没有按字母顺序判高低，也没有「最近安装的加分」。 Claude 只读一次你的任务，同时把它拿去和每一个候选 description 权衡——这跟它用来理解请求本身的， 是同一种相关性判断，不是一个写死规则的固定路由器。当恰好只有一个 description 明显合适时， 那一个触发，其余保持沉默。更难的情况，是不止一个看起来都说得过去。

  • 它是一个场域，不是一个队列。 所有已安装的 Skill 同时都是候选——Claude 实际在回答的问题是「这些里面哪个最合适」，不是「这一个合不合适，是或否」。
  • 具体程度才是决胜关键——跟幻灯片13是同一根坐标轴。 如果两个 Skill 的 description 都貌似能覆盖一个「计费」任务，那个写出了精确触发短语的——「退款原因代码」，而不是「计费系统」——会在这场接近平局的竞争中胜出，不是靠规则，而是因为它是措辞更好的那个匹配。
  • 一个含糊的 description 不会安全地失败——它会在自己都不知道正在打的仗里输掉。 这不只是「可能永远不触发」（幻灯片13的第一种失败模式）；面对一个在重叠任务上写得更锋利的同类 Skill，它可能会彻底、悄无声息地输掉这场匹配，没有任何错误提示可供察觉。
  • 真正的平局是一种设计异味，不是 Claude 的 bug。 如果两个 Skill 的 description 对同一个任务同样具体，这说明它们的范围其实是重叠的，应该被拆分或合并——不是靠更巧妙的措辞去绕过去的问题。

写一份精确的 description，从来都不只是为了让你这一个 Skill 能触发。而是为了让它能赢——赢过 同一个房间里坐着的每一个其他候选。

发现与调用 · 第4部分 · 第2步（共4步） 17 — 24
触发一个 skill 不是免费的——但保持已安装状态是免费的

一个 Skill 的代价，只在匹配那一刻付一次。CLAUDE.md 的代价，每次会话都要付一次——不管今天的任务需不需要它。

幻灯片8已经说明了，一旦一个 Skill 匹配成功，它的 SKILL.md 正文就会被加载进上下文——这是真实的 token 代价，叠加在每个已安装 Skill 每次都要付出的 frontmatter 扫描代价之上（幻灯片7）。把这个 拿去和第2周为 Ledger 打下的 CLAUDE.md 相比：CLAUDE.md 每次会话都会无条件地全文加载——不管今天 的任务是不是碰到了计费、退款，还是压根跟 Ledger 无关。这就是全部的区别所在。CLAUDE.md 是常驻 上下文；一个 Skill 的正文是条件性上下文，被挡在一次可能永远不会到来的匹配后面。

  • CLAUDE.md：常驻。 在会话开始时加载，每次会话都是，全文加载，不管跟你接下来要问的问题相关不相关。
  • Skill frontmatter：便宜且恒定。 每一个已安装 Skill 的 name 加 description 每次都会被扫描——体量小、固定，不管匹配与否都要付这份代价。
  • Skill 正文：有条件、被延后。 底下的步骤只有在 description 匹配上这个任务时才会加载。对每一个不是这个任务的任务，代价都是零——不管已经装了多少个 Skill。
  • 实际的收益是： 你可以为团队每一份反复用到的操作手册都装一个 Skill——退款、部署、事故响应，全部都可以——而不会让一次跟它们全都无关的会话把上下文预算撑爆。装了，不等于加载了。

CLAUDE.md 是你为扎根付出的税，每次会话都要交，没有例外。Skill 更像是架子上的一件工具——只有在 你真正伸手去拿它的那一刻，它才会花你任何代价。

发现与调用 · 第4部分 · 第3步（共4步） 18 — 24
四个层次，一个项目，四个不同的问题

SKILL.md、CLAUDE.md、记忆和 RAG 不是互相竞争的选项——它们是对四个不同问题的四种不同答案。

第2周给了 Ledger 三个扎根层次。这周加上了第四个。摆在一起看，每一层回答的问题，都是其他几层 回答不了的。

CLAUDE.md
它承载什么

持久、变化缓慢的项目事实——约定、架构，以及指向真正答案所在位置的指引（比如 billing-events 主题名，或公司的审计日志格式）。

何时加载、如何被找到

每次会话都无条件全文加载。不是被发现的——就是一直都在那里。

记忆
它承载什么

一份关于过去具体决策和反馈的记录，与它们发生的时间和原因绑定——按照第2周的分类方式组织（用户/反馈/项目/参考）。

何时加载、如何被找到

根据与当前任务的相关性被有选择地调取出来——不像 CLAUDE.md 那样整份倾倒，也不像 Skill 的 frontmatter 那样被扫描；相关的条目会在话题再次出现时被拉取进来。

RAG
它承载什么

任何太大或太多变、根本没法放进 CLAUDE.md 的东西——完整的 wiki 页面、过去的 PR、长篇规格文档——在查询时从底层语料库里检索出来。

何时加载、如何被找到

默认什么都不加载。一次在需要的那一刻发出的查询，会检索出具体匹配的那一块——语料库剩下的部分原封不动。

Skill（SKILL.md）
它承载什么

一套流程——一连串需要判断才能施行的步骤，不是一个事实，也不是一份语料库（幻灯片4、12）。

何时加载、如何被找到

Frontmatter 每次会话都会被低成本地拿去和每一个任务比对（幻灯片7）。完整正文只在匹配上时才加载（幻灯片8、17）——否则不花任何代价。

这些层次在同一个任务上是相互组合的，不是互相替代的。再拿第1部分的退款代码改动来说：CLAUDE.md 提供的事实是要发布到 billing-events 这个主题；记忆提供的是「项目」类别下的一条记录，说明 为什么沙箱集成测试变成了强制项（一次过去的事故，不是任何人会想到要重新声明的规则）；RAG 从一份 太长、没法内联进 CLAUDE.md 的 wiki 页面里，取出精确的审计日志字段规格；而 ledger-refund-code 这个 Skill 提供的是流程本身——把这三个事实变成一次完成的改动所需的、有顺序的那些步骤。没有任何 一个层次能单独完成这个任务。

跟第2周的「这个代码库里什么是真的」对上这周的「你要对它做什么」，是同一个问题——只是现在从一层 变成了四层，每一层都按自己的方式加载，按自己的方式被发现。

发现与调用 · 第4部分 · 第4步（共4步） 19 — 24
这个模式能推广到这门课这两个例子之外

Ledger 的退款代码和 frontend-slides，是两个数据点。这里再给出四个，来自这份工作的四个不同角落。

拿幻灯片12的清单去检验这几个例子，它们会像退款代码流程一样全部通过：它们在不同人之间反复出现， 它们是需要判断的一连串步骤，而不是单一事实或固定脚本，它们能压缩成一句诚实的话，而且跳过 某一步会有真实的代价，只是这个代价不会马上显现，而是之后才冒出来。

  • 一份部署操作手册——金丝雀发布、健康检查阈值、回滚触发条件。 每次发布都会反复出现，不管这周轮到谁值班；「如果错误率在Y分钟内超过基线X个百分点就回滚」是针对实时数据做出的判断，不是一次机械检查——这正是它不只是一个脚本的原因。
  • 一份针对你团队实际失败模式定制的代码审查清单——缺失的功能开关保护、没处理好的迁移回滚、上个季度那个坑过你的具体边界情况缺了测试。 泛泛的审查建议是一个事实（「我们要求写测试」）；你团队那份特定、来之不易的清单，正因为是用昂贵的代价换来的，才值得被打包成一套流程。
  • 一套提交信息/PR描述的约定——工单编号关联、破坏性变更标记、审查者期望看到的具体章节。 用一句话就能说清楚，在截止日期压力下也很容易被跳过，而它的代价——一个没法审查的 PR、一个没关联上的工单——会出现在别人的冲刺里，不是你的。
  • 一套事故响应流程——谁会被呼叫、记忆还新鲜时时间线上要记录什么、一份免责事后分析模板要满足什么条件才算完成。 这份清单里风险最高的一项：恰恰是在最要命的时刻，在压力下被跳过——这正是应该把它打包成 Claude 会遵循的东西、而不是靠值班工程师在凌晨三点凭空回忆的理由。

这些都不是什么稀奇的东西。它们是每一个工程组织早就有的操作手册，写了一半，躺在一份没人会在 事故进行中打开的 wiki 里——这正是 Ledger 退款代码问题的翻版，换了四个团队而已。

应用 · 梳理你的操作手册 · 第1步（共2步） 20 — 24
这周的实验 · 一个预告，不是构建规格

这周：一个真实的聊天机器人——护栏、一个评判模型、记忆、一个路由器、一个 UI。其中一个反复出现的部分，会被做成一个 Skill。

这周的实验是一个端到端搭建的、真正能用的聊天机器人：输入/输出护栏、一个用于质量控制的 LLM-as-judge 步骤、持久化记忆、一个根据任务切换模型的路由器、一个 Gradio 前端，外加 uv 在底层管理整个环境。它不是个玩具——它是一个系统，里面反复出现、且充满判断的流程足够多， 值得把其中至少一部分，按这整堂课讲的方式打包起来：做成一个 Skill，而不是每次碰它都要重新 解释一遍。完整的构建细节会在实验指南里给出，不是在这里——这只是一个预告，不是规格文档。

  • 护栏（Guardrails）——聊天机器人在一个回复被认为可以安全返回之前会运行的检查。
  • LLM-as-judge——一次模型调用，它的工作是评估另一个模型的输出，而不是生成面向用户的答案。
  • 记忆——聊天机器人跨轮次、跨会话都能调用的持久化状态，不只是在一次对话内部。
  • 路由器（Router）——决定由哪个模型处理某个请求的逻辑，而不是默认把所有东西都发给同一个模型。
  • Gradio——终端用户真正会交互的 UI 层。
  • uv——这个项目的 Python 环境是如何被管理和复现的。

现在就开始想：这里面哪个部分——一次护栏检查、评判模型的评分标准、路由器的决策逻辑——是你会希望 Claude 用同样的方式遵循两次的流程。那一个，就是你要打包成 Skill 的对象。

找出你自己团队里一两份天生适合做成 Skill 的操作手册——并且证明这一点，别只是假设。

幻灯片19给出了别人工作里的四个例子。这一页是关于你自己的。在你团队的流程里，某个地方藏着一套 一直被重新解释、而不是被打包起来的流程——把它从那份没人会在冲刺进行到一半打开的 wiki 页面里 拽出来，老老实实地拿它去过一遍幻灯片12的清单，别只凭记忆。

  • 先列出3-5个候选任务，不是一个。 部署、值班交接、代码审查、发布说明、事故事后分析、把一个服务接入 CI——不管你团队实际反复在做的是什么。
  • 把每一个都拿去过幻灯片12的五项检查： 它是否在不同人之间反复出现，它是一连串步骤而不是单一事实吗，它需要判断而不是完全一致的机械执行吗，你能用一句话说清楚吗，跳过它会不会有真实的代价。
  • 挑出过了四项或五项检查的那一两个。 其余的也不算浪费——它们现在被正确地识别成了脚本、CLAUDE.md 事实，或者还没被理解到足以打包的任务。
  • 在做任何其他事之前，先写那句一句话的 description——跟幻灯片13是同一条纪律。如果你没法那么干净地说清楚它是什么、什么时候该用，你找到的是真正的缺口，不是清单本身的失败。
  • 把你的一两个候选任务带到下次课程，准备好聊一聊 description 差一点就会误触发的地方在哪里。

清单从来都不是幻灯片12的重点——找出你团队里哪些部落知识真正值得被打包，才是重点。这一页，就是让你去找出答案的地方。

反思 22 — 24
反思 · 带到班级讨论里来

三个问题，留给你在下次课程之前好好想一想。

这不是测验——这些问题都没有标准答案会被打分。它们的用途是给下次课程开场的讨论提供种子，所以 带一个具体的答案来，不要泛泛而谈。

三个要说出口的问题
  • 想一想你团队最近一次，一套反复出现的流程在时间压力下被做错、或被跳过的情况。要让那一步不管是谁在做、不管有多赶，都能以同样的方式发生，需要具备什么条件？
  • 如果那个唯一了解你团队最混乱、也最重要的操作手册的人，明天就离职了，会失去什么——而它为什么到现在还没被打包起来？
  • 你自己在「值得为它写一个 Skill」和「一份 wiki 页面加一句 Slack 提醒就够了」之间，把界线画在哪里？说出一个对你来说正好卡在这条界线上的具体流程，以及什么因素会把它推向哪一边。

带一个真实的答案来，绑定在你工作中一个真实的流程上——不是关于「打包知识」这件事的泛泛看法。

展望接下来 23 — 24
展望下周 · 第4周

Skill 打包的是 Claude 已经知道怎么做的事。下周：给它接入它还不知道的东西的能力。

一个 Skill 打包的是一套流程——Claude 靠自己的推理、加上上下文里已有的东西去遵循的步骤。但大量 真实的工作，依赖的是活的外部系统——你的工单系统、你的部署流水线、你的内部 API——而 Claude 完全没有内置的方式去触达它们。第4周会讲模型上下文协议（Model Context Protocol，MCP）：Claude 如何直接连接到这些外部工具和数据源，而不是靠你手动把它们的输出复制粘贴进提示词里。

这周给了 Claude 一份「怎么做事」的记忆。下周会给它一双手，伸得比你的上下文窗口能到达的任何地方都要远。

收尾 24 — 24
收尾 · 这周浓缩成一句话

打包，而非提示词。

一个扎根的智能体，依然不是一个完成体。CLAUDE.md、记忆和 RAG——第2周的内容——告诉 Claude 你的 项目里什么是真的。Skill 告诉它该怎么对付这些事：一套流程，只写一次成为一份 SKILL.md， 靠 description 被发现，靠判断被遵循，而不是每次它再次出现时都从零重新解释。做得不好，它要么 永远不触发，要么在错误的任务上触发。做得好，它就跟把一段重复代码提取成一个命名恰当的函数是 同一个动作——只不过决定何时调用它的「调用者」是 Claude，靠的是判断而不是固定条件，像读一份 文档字符串那样去读你的 description，并且每次都重新调整步骤，而不是原样重放。

  • 不是每一个反复出现的任务都天生适合做成 Skill。 它必须在不同人之间反复出现、是一连串需要判断的步骤、能压缩成一句诚实的话，并且跳过它会有真实的代价。
  • description 就是全部的发现面。 文件里其余的一切，在这一个字段匹配上 Claude 眼前的任务之前，都是不可见的。
  • 渐进式披露让索引保持精简。 SKILL.md 保持为一份简短的步骤和指引清单；沉重的材料活在一跳之外，只有某一步真正需要时才会被加载。

扎根解决了 Claude 知道什么。这周解决了它做什么。下周：它能触达什么。
