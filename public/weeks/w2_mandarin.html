扎根。

上下文工程 · 记忆、CLAUDE.md 与 RAG

回顾 · 来自第1周 02 — 21
在今天之前

上周讲的是循环本身。这周讲的是循环里装的是什么。

你已经学会了在不同权限模式下，引导 Claude Code 走完感知 → 规划 → 行动 → 观察的完整循环，处理真实、混乱的代码。这个循环确实管用——但你可能已经注意到一件事：把同一个循环用在两个不同的项目上，输出质量却天差地别。有时候 Claude「一下就懂了」；有时候，你每一次会话都要重新解释一遍同样的约定。

  • 循环是机制本身。无论项目是什么，它的运行方式都一样。
  • 变化的是，循环运行时模型手头能用上的东西。
  • 今天的问题是：是什么决定了一次会话一开始就扎根，还是一开始就瞎猜？

答案就是上下文工程——这正是一个处处跟你较劲的工具，和一个早已了解你的世界的工具之间的区别。

问题所在 · 第1部分（共3部分） 03 — 21
你不填的空白，会被什么填满

垃圾进去，看似靠谱的垃圾出来。

当你提出一个含糊的问题时，模型不会停下来问你到底是什么意思——它会用见过的、针对这类请求最常见的模式，去填补这个空白。这种模式放在一般情况下往往说得通，但放到你的具体代码库里，就是错的。

没有上下文 「给支付调用加一个重试。」 结果：一个通用的指数退避重试，没有幂等键，无视了项目里现成的 retryWithBackoff() 辅助函数——而且重试时真的有可能让客户被重复扣款。
有上下文 同样的提示，但有 CLAUDE.md 扎根 CLAUDE.md 里已经写明了这个重试辅助函数和幂等性要求。结果：一次就接对了——没有重复扣款风险，也不用重新解释一遍。

模型没有问题。缺的是扎根。

问题所在 · 第1部分（共3部分） 04 — 21
每一个 token，都在争夺注意力

上下文是预算，不是愿望清单。

每个模型的上下文窗口都是有限的。所有放进去的东西——系统指令、对话历史、文件内容、检索到的文档——都共用同一份预算，互相争夺模型的注意力。往窗口里塞无关的内容，不只是浪费空间；即使技术上「塞得进去」，它也会稀释真正有用的信号。

~8% 扎根
~35% 对话历史
~32% 检索文档
~25% 输出余量
扎根材料 —— CLAUDE.md、系统指令。体量小、固定、没有商量空间。
对话 —— 每一轮都在增长，不管还相关不相关。
检索文档 —— 按需取用，是你真正能掌控的那根杠杆。
余量 —— 必须留给模型自己的输出。

这只是典型会话的示意比例——实际比例会因任务而变化。

注意力，才是模型最稀缺的资源——不是 token 数量。

问题所在 · 第1部分（共3部分） 05 — 21
听起来合理，不代表是对的

它不会拒绝回答。它会很自信地——瞎猜。

上下文缺失时，模型不会报错，也不会说「我不知道你们的约定」。它会给出一个表达流畅、听起来很合理、却悄悄出错的答案——这比明显的失败更危险，因为它能轻松通过一次粗略审查。

一个悄悄出错的猜测

Claude 给一个 API 响应加了一个新字段。命名完全符合文件里现有的约定。但它也悄无声息地弄坏了三个下游消费者——没有人提到过它们，因为项目里压根没写它们的存在。

解决办法不是写一个更好的提示词。而是更好的扎根——而扎根，分三个层次。

三个层次 · 第2部分（共3部分） 06 — 21
一种知识，对应一个层次

三种不同的问题。三个不同的层次。

CLAUDE.md、记忆和 RAG，回答的其实是同一个问题——「模型怎么知道它需要知道的东西？」——但它们各自针对的是不同形状的问题。用错了层次，原本该解决问题的那一层，就白白浪费了。

CLAUDE.md / AGENTS.md
静态的项目扎根 每次会话都会加载，每次内容都一样。
最适合 约定、架构说明，以及「不要做X」这类规则。
始终存在，每次内容相同
记忆
跨会话持久保存的事实 随着你们一起工作不断累积。
最适合 已做出的决策、了解到的偏好，以及只需说一次的纠正。
随时间增长；能在全新会话中留存
RAG
查询时动态检索 只有相关时才会被取用。
最适合 庞大或不断变化的语料——代码库、文档、工单——大到任何上下文窗口都装不下。
每次查询内容不同，按需取用

用对了层次，你就不用再为另外两层付出代价。

CLAUDE.md 细看 · 第2部分（共3部分） 07 — 21
claude 在碰任何东西之前，先读的那个文件

一个文件，每次会话开始时都会被读一遍。

CLAUDE.md 不是写给人看的文档——它是模型在碰你的代码之前，最先读的东西。写进去的内容，就再也不用说第二遍。

01项目概览
写什么

一段话：这个项目做什么，谁在用，技术栈是什么。

为什么重要

几秒钟就能让一次全新会话进入状态，不用反复探索式阅读。

02约定
写什么

命名、格式、文件结构，以及已经存在的辅助函数。

为什么重要

免得这些东西在新函数里被悄悄重新发明一遍。

03该做 / 不该做
写什么

明确的护栏——比如「永远不要编辑生成的文件」「提交前先运行X」。

为什么重要

这些规则，人类同事靠日积月累就能心领神会；模型需要你把它写出来。

04架构说明
写什么

任何单个文件都看不出来的决策——比如为什么会有这个重试辅助函数，为什么两个相似的服务要分开。

为什么重要

没有这些说明，一次「清理」就可能悄悄推翻一个本来刻意做出的选择。

05构建 / 测试命令
写什么

要运行的具体命令——lint、测试、构建、部署。

为什么重要

这样智能体能自己验证工作成果，而不是靠猜。

如果你已经解释过不止一次，它就该写进 CLAUDE.md。

记忆细看 · 第2部分（共3部分） 08 — 21
值得被特意记住的东西

会话结束后，什么应该被留下来？

CLAUDE.md 是静态的——写一次，每次会话都一样。记忆不同：它会不断累积，怎么组织由你决定。下面是一种可行的分类方式——不是 Claude Code 强制规定的格式，只是一种值得借鉴的做法。

01用户
记录的内容

你的角色、偏好，以及你喜欢的工作方式。

示例

「喜欢简短的回复，合并前会 review 每一处改动。」

02反馈
记录的内容

纠正和确认——什么该避免，什么是有效的。

示例

「集成测试里不要 mock 数据库——之前出过事故。」

03项目
记录的内容

决策、截止日期，以及代码本身看不出来的持续性背景信息。

示例

「认证重写是合规驱动的，不是代码清理——范围要按这个来定。」

04参考
记录的内容

指向外部真正、最新答案所在位置的指针。

示例

「Bug 都记录在 Linear 的 INGEST 项目里，不是 GitHub Issues。」

记忆不是每次对话的逐字记录——而是少数几个、值得永远不用再解释一遍的事实。

RAG 细看 · 第2部分（共3部分） 09 — 21
靠检索，不靠死记

有些语料库，大到根本没法整个交出去——那就别整个交。

一个200个文件的代码库，一份记录了五年决策的 wiki，一份客服工单存档——这些东西没有一个能塞进上下文窗口，而且对任何单一问题来说，里面大部分内容都是无关的。RAG 的工作，就是只取出真正相关的那一小片，并且在需要的那一刻取出来。

步骤 1 分块与嵌入 把文档拆成小块，把每一块转换成一个能体现其含义的向量。
→
步骤 2 存储 把这些向量建立索引，这样任何新问题的最接近匹配都能被快速找到。
→
步骤 3 检索 找出和当前问题在含义上最接近的那些块。
→
步骤 4 增强 在模型回答之前，把这些块放进上下文里。

CLAUDE.md 和记忆，是模型一直都有的东西。RAG，是它按需去要来的东西。

选对层次 · 第2部分（共3部分） 10 — 21
让层次匹配问题的形状

一个简单的判断标准：它多久变一次，体量有多大？

稳定的事实
→ CLAUDE.md 很少变化，体量小。「我们用 pnpm，不用 npm。」「测试放在 /tests，结构对应 /src。」
持久的决策
→ 记忆 随时间累积。「上个季度我们否决了 GraphQL——见 ADR-012。」「这位用户想要 PR 描述，不要行内注释。」
庞大或不断变化的语料
→ RAG 大到装不下，而且还在持续增长。整个代码库。客服工单历史。产品 wiki。

大多数项目需要这三层都用上。大多数上下文债务，都来自跳过了其中一层。

上下文债务 · 第3部分（共3部分） 11 — 21
在沉默中累积的债务

上下文债务，是技术债务那位更安静的表亲。

技术债务，是那些能跑、但你每碰一次成本就更高一点的代码。上下文债务是同样的想法，往上挪了一层：智能体要把活干好真正需要知道的东西，和实际已经扎根在 CLAUDE.md、记忆与可检索文档里的东西，两者之间的缺口。它不会表现为一个失败的测试。它表现为：每一次会话，都比本该有的样子更困惑一点。

  • 这个月，你已经第三次跟 Claude 解释同一个约定了。
  • 它很自信地违反了一条确实存在的规则——只是这条规则它根本看不到。
  • 「上周明明不是这样的」——却没有任何记录说明改了什么、为什么改。
  • 一个新来的同事，无论是人还是智能体，都要花上好几天才能上手，因为什么都没写下来。

和技术债务一样，它会悄悄地越滚越大——直到某次会话搞砸到你不得不注意为止。

上下文债务的解剖 · 第3部分（共3部分） 12 — 21
五种你很熟悉的失败模式

它会以五种方式出现。

01缺失的 CLAUDE.md
表现形式

没有扎根文件，或者只有一份一年前 README 里的三句话。

代价

每次会话都从零开始；约定要么被重新解释，要么被重新瞎猜。

02过时的记忆
表现形式

曾经是对的、已保存下来的事实，但项目早已发展到了别的阶段。

代价

自信满满地给出错误答案，引用的还是一个早已被推翻的决策。

03没有示例
表现形式

规则说得很抽象——「遵循我们的约定」——却没有任何具体的东西可以对照。

代价

模型会按自己的方式去理解这条规则——听起来合理，却很少是对的。

04相互冲突的指令
表现形式

CLAUDE.md 说一套，代码注释说另一套，记忆里又是第三套。

代价

模型会悄悄选一个；你只有等出问题了才会知道它选了哪个。

05未经扎根的 RAG 语料库
表现形式

一份只建过一次、从未更新过的检索索引，指向的还是已经过时的文档。

代价

检索「成功」了——它给出的答案自信满满、格式工整，却早已过时。

这些都不是什么稀奇的问题。这五种都很常见——而且每一种单独拿出来，修复起来都比你想象的要快。

桥接篇 13 — 21
你即将要扎根的这个项目

从理论，到一次真正的审计。

到目前为止，每一层都还停留在抽象的讲解里。现在，我们来真的——在一个你们谁都没见过的项目上，它有着大多数真实项目都有的那种上下文缺口：没有 CLAUDE.md，决策埋在旧的 Slack 讨论里，一个好几个月没人打开过的 /docs 文件夹。

认识一下 Ledger——一个即将被好好扎根的订单/计费服务。

实验预告 · 第4部分 14 — 21
现在轮到你了

审计它。为它扎根。看看差别。

今天的实验：拿 Ledger——一个真实可运行、却完全没有扎根的订单/计费服务——通过四个步骤，给它一份 CLAUDE.md、一条记忆条目，以及一个指向它自己文档的指引。然后用同一个问题问 Claude 两次：扎根之前，和扎根之后。

  • 一个真实的订单/计费服务，已经存在两年，由一个早已转去做别的事的团队搭建。
  • 没有 CLAUDE.md。一个好几个月没人打开过的 /docs 文件夹。约定只存在于人们的脑子里。
  • 你的任务：用四个步骤为它扎根，然后观察输出是否真的发生了变化。
  • 留意：你选择写下什么、留下什么不写——这个选择本身，才是真正的技能。
实验演练 · 第1步（共4步） 15 — 21
先冷读一遍，什么都别写

像 Claude 一样，冷读一遍 Ledger。

在写任何东西之前，先审计它：以全无背景知识的状态重新打开这个代码库，试着回答「要安全地修改这段代码，我需要知道什么？」记下每一处你靠猜、靠假设，或者要翻 git 历史、翻 Slack 才能弄明白的地方。

来自 ledger

支付重试逻辑里，没有任何注释解释它的幂等键要求。唯一写下过这件事的地方，是一条六个月前的 Slack 讨论。

你刚才费力去找的那些东西——那才是真正的审计。一旦你亲眼盯着它，上下文债务就一点都不抽象了。

实验演练 · 第2步（共4步） 16 — 21
对什么才是真正承重的内容，要狠一点

只写下那些你需要解释第二遍的东西。

把审计结果变成一份 CLAUDE.md。诱惑在于想把所有东西都记下来——一定要克制住。一份十页长的 CLAUDE.md，本身就是一种上下文债务；它占用的，正是你在第1部分看到的那份预算。坚持用前面那五个部分——概览、约定、该做/不该做、架构说明、测试命令——并且对什么才是真正承重的内容，要狠一点。

来自 ledger

第1步里那条幂等键约定，在「该做 / 不该做」下面变成了一行：「调用支付网关时永远不能不带幂等键——参见 PaymentClient.charge()。」

好的扎根都是简短的。这不是一种限制——这就是重点本身。

实验演练 · 第3步（共4步） 17 — 21
记的是现在为真的事，不是永远为真的事

记下那个不在任何文件里的决策。

CLAUDE.md 记录的是永远为真的事。记忆记录的是现在为真、在工作过程中了解到的事。今天的任务：找出一个埋在 Slack 或团队集体记忆里的持久决策——比如「我们决定 v1 不支持部分退款」——把它存成一条项目记忆，这样下一个人，或者下一次会话，就不用再费劲重新发现一遍。

来自 ledger

「部分退款功能从 v1 推迟（Slack，三月）。要重新引入，需要产品方批准，不只是一个工程上的修复。」一句话，存一次，再也不用重新争论。

一条记忆，写下来很便宜，丢掉了很昂贵。

实验演练 · 第4步（共4步） 18 — 21
闭合循环

同一个问题，问两次。对比两次的答案。

让 Claude 连接到 Ledger 现有的 /docs 文件夹，然后用一个你真的会问这个服务的问题，问它两次——一次在任何扎根之前，一次在扎根之后。

扎根之前 「我能安全地给 Ledger 加上部分退款功能吗？」 一份通用的实现思路，完全不知道这个功能已经被刻意推迟过——悄悄重新打开了一个已经关闭的决策。
扎根之后 同一个问题，同一个服务 正确地把那条记忆条目翻出来——「从 v1 推迟，需要产品方批准」——而不是把它当成一个从零开始的功能请求来处理。

这份差别，就是你刚刚建立起来的一切，被一组答案的对比清清楚楚地照了出来。

轮到你了 19 — 21
开始

打开实验指南。

  • 审计——冷读一遍，记下每一个缺口。
  • 写 CLAUDE.md——五个部分，不多不少。
  • 搭建记忆——一个持久决策，记一次就好。
  • 让 Claude 连接文档——然后问你真正的问题，扎根前和扎根后各问一次。

大约35–40分钟。之后我们再集合。

应用 · 你的练习 20 — 21
本周的练习

审计你自己项目的上下文债务。

  • 选一个你经常参与的真实项目。
  • 做同样的审计：一次全新的会话，需要知道哪些根本没写在任何地方的东西？
  • 为它写一份，或改进现有的 CLAUDE.md——五个部分，不多不少。
  • 至少搭建一条持久记忆——记下一个总是差点又要被重新解释一遍的决策。

把你最大的发现带到下次课程——不管是你自己的，还是别人的。
