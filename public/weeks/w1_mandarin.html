回顾 · 来自第0周 02 — 22
在今天之前

你已经知道执行框架是什么——从通用层面而言。

五大组成部分，一个循环：感知 → 规划 → 行动 → 观察，由工具、上下文、权限和记忆共同支配。这就是第0周建立的共享词汇。

  • 工具——执行框架可以调用的能力。
  • 上下文——模型当前能够"看到"的内容。
  • 权限——它在无人监督时可以做什么。
  • 记忆——在不同会话之间持续保留的内容。

今天，这一切都将变得具体——因为 Claude Code 正是这套模式的一个具体实例，而不是全新的另一套。

桥接篇 · 第1部分 03 — 22
从通用模式到具体工具

Claude Code 正是这同一套循环的一种具体、带有明确主张的实现。

同样的五大组成部分。同样的循环。但现在有了一组具体的工具、一组具体的权限模式，以及一个具体的载体——你的终端，在你真实的代码仓库上。今天的一切，都会让第0周的抽象概念变得具体——而这一切，要从一个会彻底改变你使用这个工具方式的关键区分开始。

首先：聊天与指挥。

核心区分 · 第2部分 04 — 22
这个区分将改变一切

聊天和指挥看起来很像。但它们完全不是一回事。

浅水区 聊天 一问一答。你问，它答，然后你拿着结果自己动手去完成工作。循环发生在你的脑子里，而不是工具里。
前沿地带 指挥 把一个有边界的多步骤任务交出去。智能体会运行自己的感知 → 规划 → 行动 → 观察循环，只在你指定的地方才向你确认。

从这里开始的每一周，都默认你在"指挥"。今天的实验环节，就让你亲自上手。

落到实处 · 第2部分 05 — 22
一个真实项目，不是假设案例

为客服代表打造一套基于 RAG 的智能体系统，从来都不是一场"聊天"。

目标：打造一个检索增强型智能体，帮助客服代表准确回答政策与优惠相关的问题。这项工作是连续数天的多步骤集成——接入 Amazon Bedrock 作为底层模型，连接我们内部的部署环境，并集成一个优惠活动 API 以及其他内部工具。这些事情，不可能在一次提示-回应中完成。

  • 阅读并改写了跨多个服务的现有集成代码。
  • 为基于 Bedrock 的检索流水线编写并运行了测试。
  • 在多个文件之间反复迭代，而不是在一个窗口里完成——每一步都为下一步提供了输入。
  • 这就是智能体循环，运行在一个真实系统上，承担着真实的风险。
解构，落到具体 · 第1部分 06 — 22
同样的五个部分，现在有了具体名字

这就是第0周那五大组成部分，在 Claude Code 中分别对应的具体内容。

01模型 Model
是什么

Claude 本身。

在循环中的角色

负责生成"规划"这一步——根据它当前能看到的一切，决定接下来调用哪个工具。

CLAUDE.md、对话内容，以及它读过的文件。

04权限 Permissions
是什么

权限模式——默认、规划、自动批准、绕过。

在循环中的角色

"行动"步骤的护栏——你很快就会看到，这是本周影响最大的一环。

05记忆 Memory

项目级的 CLAUDE.md（位于代码仓库根目录），加上 ~/.claude 下的用户级设置与记忆。

循环实战 · 第1阶段（共4阶段） 07 — 22
01 感知 Perceive

Claude Code 会读取你的提示词、代码仓库当前的状态，以及目前为止每一次工具调用的结果——这就是"感知"，循环中的每一步都是如此。

来自那个 rag 项目

在那个项目里，"感知"意味着在写下第一行代码之前，先读懂现有的 Bedrock 集成代码、内部部署环境的配置，以及优惠活动 API 的文档。

循环实战 · 第2阶段（共4阶段） 08 — 22
02 规划 Plan

它会决定下一步调用哪个工具——读这个文件？跑这个测试？改这个函数？——完全基于它刚刚感知到的内容。

来自那个 rag 项目

在那个项目里，"规划"意味着要做判断：接下来该看嵌入流水线，还是先看 API 客户端？Claude Code 在每一步都会做同样的取舍判断。

循环实战 · 第3阶段（共4阶段） 09 — 22
03 行动 Act

它会真正执行这个计划——落地在磁盘上——通过 Bash、Edit、Write 以及其他每一个工具。这不是聊天框里的一句建议，而是一次真实的改动。

值得细想

"指挥"这个说法，从这一步开始就不再只是比喻了。无论它在"规划"阶段决定了什么，现在都会真的去做——这正是为什么下一个阶段，以及本周的权限模式，会如此重要。

循环实战 · 第4阶段（共4阶段） 10 — 22
04 观察 Observe

这次行动的结果——测试通过、测试失败、文件的新内容——都会成为新的上下文。循环再次开始时，这些新信息已经被"感知"过了。

↻ 感知 → 规划 → 行动 → 观察 → 循环往复，直至任务完成
权限模式 · 本周新增的一层 11 — 22
究竟是什么在掌控"行动"

四种模式，四种截然不同的摩擦程度。

默认模式每次写入前先询问
会发生什么

每一次文件修改或风险命令，都会暂停，等待你逐一批准。

适用场景 / 取舍

不熟悉的代码、高风险的改动。更安全，但更慢。

规划模式先提案，再批准
会发生什么

Claude 会先完整列出它的方案，然后才采取任何行动。

适用场景 / 取舍

适合多步骤或不太明确的任务。只需审查一次，而不是反复审查——但前提是你要真的读完那份计划。

自动批准编辑先应用，后审查
会发生什么

修改会立即生效；你之后再审查改动内容，而不是逐一批准。

适用场景 / 取舍

在可信的范围内快速迭代。快——直到你不再真正去审查为止。

绕过权限什么都不会暂停
会发生什么

整个循环从头到尾无人值守地运行。它的启用方式和前三种不同——是一个启动参数，而不是你在会话中途切换进去的模式。

适用场景 / 取舍

适合沙盒环境、低风险的批量工作。杠杆最大，爆炸半径也最大。

前三种模式，是你在会话过程中可以切换的。"绕过"则是一个独立、风险更高的开关，需要你提前、主动地做出选择。

权限模式 · 真实的代价 12 — 22
真实的代价，不是假设情形

曾有一次，不留神的自动批准，让我们一套正常运行的 RAG 系统付出了代价。

在那个客服 RAG 项目里，当时的习惯是自动批准编辑和文档导入，而不会逐一仔细审查。有一次，这个习惯导致一批早已过期、被替换掉的政策文档被导入了知识库。直到准确率已经下降，才有人发现问题——修复的办法是回退到之前可用的版本，并重新完成那部分工作。

说得精确一点：那次自动批准发生在文档导入流水线里，并不是 Claude Code 自身的权限模式——这是两个不同的系统，失败的表现方式也不同。一次糟糕的代码改动，会在 git diff 里看得清清楚楚；但知识库里的一份糟糕文档，通常要等到答案变差了才会被发现。但导致问题的那个习惯——不看就批准——正是 Claude Code 的权限模式，能帮你养成、也能帮你打破的那个习惯。

问题不在于那个设置本身。问题在于用它的时候没有用心。

权限模式不是一次设置选择——而是你要养成的一种习惯
终端，就是杠杆 13 — 22
为什么是终端，而不是聊天窗口

终端，是指挥智能体杠杆最大的载体。

  • 跨多个文件的修改，一次性应用，而不是一个个手动复制粘贴。
  • 真正的测试套件，真正被运行——不是口头描述，而是实际执行。
  • Git，真正被提交——留下你可以查看和回退的历史记录。
  • 可以和你已经在用的其他所有命令行工具组合使用。
它解决的多语言难题

不同的产品往往需要不同的语言和环境——这边是 C，那边是 Java，另一边又是 Python。无论如何，Claude Code 的工作方式始终一致：一套执行框架，而不是按语言各搞一套工具。

探索式工作 14 — 22
不是每个任务一开始就有清晰的需求

有时候，接入一个现有环境，意味着要先探索，再行动。

当接入现有系统的说明并不完整时，"指挥"智能体的一部分工作，就是先让它去探索——读代码、弄清楚事情是怎么接起来的——然后才进入产出结果的部分。

这不代表你选错了任务。这很正常。在今天的实验环节留意它，本周你自己的练习中也会再遇到。

重构它。写测试。运行它们。实时观察循环的运作。

  • 一个真实的、故意写得很乱的随机森林客户流失预测脚本。

实验演练 · 第1步（共4步） 16 — 22
把任务交出去

一次指令，而不是来回的聊天。

打开 week1-lab-repo/churn_model.py，把整个任务一次性交给 Claude Code：重构成干净、命名清晰的函数，然后为核心预测逻辑编写测试。

这就是交接的瞬间——从这里开始，智能体会运行它自己的循环。

实验演练 · 第2步（共4步） 17 — 22
去观察，而不只是等待

观察它感知与规划——不是一次性的，而是反复发生的。

在第一次修改之前，它会先读文件、构思方案——但在真实的重构工作中，它不会止步于此。它会在每次修改之间反复重新阅读、重新规划：检查一个函数，写出来，再检查下一个，再调整。"感知"与"规划"会贯穿整个任务持续发生，而不只是在最开始出现一次。

如果你只看最终的 diff，就会错过本周真正新出现的部分。

实验演练 · 第3步（共4步） 18 — 22
这一次，是故意的

在任务进行中，主动切换一种不同的权限模式。

用一种你一开始没有选用的模式，重新做一小段任务。仔细留意循环的"感觉"发生了什么变化——而不只是看它有没有成功。

这正是第12页提到的那个习惯，从一个你已经习以为常、不再留意的默认设置，变成你主动做出的选择的那一刻。

实验演练 · 第4步（共4步） 19 — 22
把循环闭环

运行测试。确认全部通过。留意它是否进行了自我修正。

运行新写的测试，以及脚本本身。如果某个测试一开始失败了，留意接下来发生了什么——它是否先读懂了失败原因，修复之后，才告诉你任务完成？

这种自我修正，正是"观察"这一步该做的事，分毫不差。
